# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"FN Concretera" — a Flutter app for a concrete company. Note the package name in `pubspec.yaml` is `fn_concretos`, even though the directory/repo is `my_flutter_app`.

The app has grown from a UI-only prototype into a role-scoped mobile client with real backend calls for auth and for one office workflow (credit authorization), plus several feature areas that are still mock/local state. There's no single "the app does X" description — which parts are real vs. mocked varies screen by screen (see Architecture below), so check the specific screen before assuming either way.

`vistas.md` (repo root) is the product spec this build follows: it defines the three roles this app targets (Operador de Olla, Operador de Bomba, Dirección) and explicitly calls out backend gaps that block real functionality (e.g. `InformePesadora` has no service/controller/DTO yet; `ClienteService.estadoCuenta` is a stub that always answers "finanzas-service aún no está disponible"). Read it before deciding whether a feature needs backend work first or can just be wired up.

## Commands

- Install dependencies: `flutter pub get`
- Run the app (choose a connected device/simulator): `flutter run`
- Static analysis (uses `flutter_lints` via `analysis_options.yaml`): `flutter analyze`
- Format code: `dart format .`
- Run tests: `flutter test` (there are currently no test files in the project)
- Build platform targets as needed: `flutter build apk`, `flutter build ios`, `flutter build macos`, `flutter build web`, etc.

There is no CI config and no custom build scripts — this is a stock `flutter create` project structure. Native Android/iOS projects require a Google Cloud API key with "Maps SDK" and "Navigation SDK" enabled (see `route_navigation_screen.dart` below) — without it the map loads blank/greyed out and in-app turn-by-turn errors out; the Navigation SDK is billed separately from the Maps SDK. `local_auth` (Face ID/Touch ID, see `auth/biometric_service.dart` below) needed two native changes to work at all: `MainActivity.kt` now extends `FlutterFragmentActivity` instead of `FlutterActivity` (the plugin's Android biometric prompt requires a `FragmentActivity` host), and `ios/Runner/Info.plist` has `NSFaceIDUsageDescription`. Known gap: Android's `styles.xml` `LaunchTheme`/`NormalTheme` still parent off plain `@android:style/Theme.*`, not an `AppCompat`/`Theme.DayNight` theme — the plugin's README warns this can crash the biometric dialog on Android 8 and below; not fixed here since it'd mean migrating the whole app's native theme, out of scope for what was asked (this app's `minSdk` is 24, so that risk window is Android 7.0–8.1 devices specifically).

## Architecture

`lib/` is organized by feature folder, each holding its screen(s) plus any content specific to that screen; `lib/widgets/` holds components shared across features — `bottom_nav_bar.dart` (below), `evidencia_viewer_screen.dart` (`EvidenciaViewerScreen`, the pinch-to-zoom full-screen photo viewer, now shared by `vehicle/`, `deliveries/`, and `profile/`), `app_feedback.dart` (`AppSnack` — themed success/error/info snackbar, replacing plain `ScaffoldMessenger`/`SnackBar` calls), `field_group.dart` (`FieldGroup`, the rounded card container for grouping form fields), `info_pill.dart` (`InfoPill`, the small icon+label chip used on list cards), `whatsapp_button.dart` (`WhatsappButton`/`abrirWhatsApp`, opens a `wa.me` deep link for a contacto's teléfono; its icon is `font_awesome_flutter`'s `FontAwesomeIcons.whatsapp` — the only place in the app pulling in a third-party icon font instead of Material Icons, since the WhatsApp brand glyph isn't one), and `contacto_card.dart` (`ContactoCard`, shows a resolved `ClienteContacto`'s nombre/cargo/teléfono plus a `WhatsappButton`, shared by `direccion/PedidoDetailScreen` and `deliveries/DeliveryDetailScreen`). `lib/theme/app_colors.dart`'s `AppColors` is the single source of truth for brand/status colors and the theme-aware card-surface/text helpers described under Conventions below — it replaced dozens of screens each redeclaring their own local color constants, which had already drifted into inconsistent literals in a few places; import it rather than adding a new local constant. Screens navigate via `Navigator.push`/`pushReplacement` with `MaterialPageRoute` — there is no named-route table or router package, and no state-management package (no Provider/Riverpod/Bloc) — each screen manages its own local `State`. `main.dart`'s `themeNotifier` (a top-level `ValueNotifier<ThemeMode>`, default `ThemeMode.dark`, that `MaterialApp` listens to) and `AuthService`'s static session fields are the only pieces of state shared across screens; both use the same "static field, no package" pattern rather than introducing one.

**Navigation is role/permission-branched, not a single fixed flow.** `main.dart` → `SplashScreen` (plays `assets/video/splash.mp4` via `video_player` to completion, or falls straight through on load failure — while it plays, `AuthService.restoreSession()` runs in parallel off a persisted refresh token so the network round trip isn't extra wait time on top of playback) → either `LoginScreen` or straight to the post-login destination, via the shared `destinationForSession()` helper (`auth/login_screen.dart`), then routed by role/permission:
- Role name in `roles.dart`'s `rolesConAppMovil` (`Operador de Olla`, `Operador de Bomba`) → `home/HomeScreen` (field-ops shell: Entregas/Vehículo/Perfil tabs).
- Otherwise, holding the `pedidos.autorizar_credito` permission → `direccion/DireccionHomeScreen` (Autorizaciones/Rutas/Perfil tabs).
- Anyone else → `auth/RoleUnavailableScreen` (explains the role has no mobile screens yet, points to the desktop system, offers logout).

Both shells reuse the same tab pattern: all tabs stay mounted and are cross-faded (`AnimatedOpacity` + `AnimatedScale`, not `IndexedStack`) so tab state survives switching, with a floating `widgets/bottom_nav_bar.dart` (`BottomNavBar`, icon-only pill nav, active item gets a solid accent-colored circle; exposes `BottomNavBar.clearance(context)` for scrollable screens to pad their bottom content).

Dirección's routing is deliberately by *permission*, not role name, per a comment in `direccion/comercial_service.dart`: the backend's roles-controller can reassign permissions to a different/renamed role independently of this app, so hardcoding a role-name check would silently break if that happens. `auth/roles.dart` keeps a static `catalogoRoles` mirroring the backend's `/roles` catalog purely so screens can show a role's Spanish name/description without a network round trip.

### Real backend calls vs. mock data — check per screen

- **`auth/auth_service.dart`** (`AuthService`) — talks to the real `auth-service` sandbox (`https://fnconcretos.app/sandbox/auth`, see its `/v3/api-docs`). Session (access/refresh tokens, `username`, `rol`, `permisos`, `mfaHabilitado`, `idEmpleado`) lives in static fields, refreshed transparently before each authenticated call (`_ensureFreshToken`). The refresh token is also persisted via `flutter_secure_storage`, so `restoreSession()` (called from `SplashScreen`) can log the user back in silently across app restarts without re-prompting for credentials; logout/refresh-failure clears the stored token. Covers login, MFA enroll/verify (TOTP), forgot/reset/change password, logout. `LoginScreen` handles `MfaRequiredException` with an in-place TOTP dialog. `POST /auth/validate` is deliberately unimplemented — it's an API Gateway/inter-service introspection endpoint, not something a mobile client calls. The API docs mark MFA enrollment as mandatory for Dirección/Pagos, but the backend doesn't block login over it; the app enforces that itself — `ProfileScreen`'s MFA tile shows real status from `mfaHabilitado`, and `direccion/DireccionHomeScreen` shows a one-time-per-session dialog nudging enrollment when `mfaHabilitado == false` (deliberately dismissible with "Más tarde" rather than a hard lock, since there's no confirmed backend-side enforcement to mirror). Pagos isn't affected — it has no mobile screens at all (not in `rolesConAppMovil`), so it never reaches a screen where this could be enforced. **Face ID/Touch ID quick login is a local device gate, not a backend factor**: `AuthService.biometricHabilitado` (persisted via `flutter_secure_storage`, toggled from `ProfileScreen`'s "Seguridad" group, only shown when `auth/biometric_service.dart`'s `BiometricService.disponible()` says the device supports it) gates whether `SplashScreen` routes a restored session through `auth/biometric_lock_screen.dart`'s `BiometricLockScreen` before letting it into the app. Enabling it (`AuthService.habilitarBiometria()`) implicitly turns on refresh-token persistence too, even if "Recordar sesión" wasn't checked at login — otherwise there'd be nothing for Face ID to unlock next launch. There is no backend concept of biometric auth; this never touches `auth-service`, it only decides whether *this device* recognizes whoever is holding it before handing over an already-restored session — don't confuse it with MFA above, which the backend does know about.
- **`direccion/comercial_service.dart`** (`ComercialService`) — talks to the real `comercial` sandbox (`https://fnconcretos.app/sandbox/comercial`), reusing `AuthService.authHeaders()` for bearer auth. Backs `AutorizacionesScreen` (live list of pedidos pending credit authorization) and `PedidoDetailScreen` (cliente + estado de cuenta lookup, aprobar/rechazar). A `Cliente` has no phone of its own — contact info lives on its named `ClienteContacto`s (`GET /clientes/{id}/contactos`; a cliente can have several, e.g. "Residente de obra" vs. "Compras"), and *which* contacto is the right one for a given pedido depends on the obra: `GET /obras/{obraId}/clientes` returns that obra's cliente↔contacto pairings (an obra can have more than one cliente tied to it, e.g. shared job sites), each optionally naming a `contactoId`. `ComercialService.contactoParaEntrega({obraId, clienteId})` does both lookups and returns the resolved `ClienteContacto?` — null if no contacto is assigned for that pairing. `widgets/contacto_card.dart`'s shared `ContactoCard` renders it (nombre/cargo/telefono) plus a WhatsApp button when `telefono != null`, on both `PedidoDetailScreen` and `deliveries/DeliveryDetailScreen` (see `deliveries/` below) — the button itself is `widgets/whatsapp_button.dart`'s `WhatsappButton`, which opens a `https://wa.me/` deep link (via `url_launcher`) with Mexico's `52` country code prefixed onto the backend's plain 10-digit `telefono`. `EstadoCuenta.disponible == false` means the estado-de-cuenta call is answering from a stub, not real account data — surface that distinction, don't treat a stubbed response as a real "cliente al corriente". `pedido.dart` also holds `Obra` (`obtenerObra`) — a pedido's job site, with the lat/lng used for maps/navigation. `Pedido.volumenEntregadoM3`/`volumenPendienteM3`/`estatusGeneral` (`'parcial'`/`'completo'`) now update for real as each remisión gets firmada — `operaciones-service`'s `RemisionService.registrarFirma` calls an internal `comercial-service` endpoint (`PATCH /pedidos/{id}/registrar-entrega`, not in the public API docs, not called by this app directly) that accumulates delivered volume and recalculates status server-side. `PedidoDetailScreen`'s `SummaryCard` shows this as a progress bar once any volume has been delivered.
- **`operaciones/operaciones_service.dart`** (`OperacionesService`) — talks to the real `operaciones` sandbox (`https://fnconcretos.app/sandbox/operaciones`), same auth-header pattern as `ComercialService`. Lives in its own top-level folder (not under `direccion/`, despite originating there) because it's consumed by `direccion/`, `deliveries/`, and `vehicle/` — same reasoning as `auth_service.dart` living in `auth/` rather than any one screen's folder. Backs: `direccion/PedidoDetailScreen`'s "Ubicación en vivo" section (fetches the pedido's remisiones via `GET /remisiones?pedidoId=`, then polls `GET /remisiones/{id}/ruta` every 15s to render current position + trail on a `GoogleMapsMapView` — read-only map view from the same `google_navigation_flutter` package used for driving navigation, no extra dependency/API key needed; a pedido can have more than one remisión — e.g. olla and bomba, or several truck loads splitting one pedido's total volume — so this section renders one live-tracking card per remisión found, each showing that remisión's own conductor id and volume (`metrosCargados`/`metrosSolicitados` — not the pedido's total — no employee-name lookup exists in this app, so it's shown as a raw id rather than a fabricated name)); `deliveries/EntregasService` (below), via `programacion-produccion` and `remisiones`; `asignacionesPorPedido`/`AsignacionResumen` also live here (a real endpoint, `GET /asignaciones?pedidoId=`) but as of a bug fix are no longer called by `EntregasService` — it answers a different question than "which conductor owns this pedido" and can come back empty for a pedido that already has a remisión with a conductor on it (confirmed against real sandbox data: pedido 20 had an empty `/asignaciones` response despite an existing remisión with `conductorId` set), which was silently hiding otherwise-ready deliveries; the hito state machine (`avanzarHito`, `remisionDetalle`) and GPS reporting (`enviarPosicion`) also used by `deliveries/`; `pruebas-concreto-fresco` field tests; and the `vehiculos`/`mantenimientos`/`pendientes-vehiculos`/`documentos` family of endpoints backing `vehicle/` (below). Two module-level permission constants gate write calls: `permisoOperarRemisiones` (`'remisiones.operar'`, required for `enviarPosicion`/`avanzarHito`/`registrarPruebaConcreto`) and `permisoReportarPendienteVehiculo` (`'vehiculos.reportar_pendiente'`, required for `registrarPendienteVehiculo`). `remisionesEnRuta()` backs `direccion/RutasActivasScreen` ("Rutas" tab) — a fleet-wide consolidated map, not scoped to one pedido like "Ubicación en vivo" above: it calls `GET /remisiones` with no filter at all (both `pedidoId` and `estatus` are optional per the OpenAPI schema, same as the unfiltered `vehiculos()` call) and narrows client-side to the statuses that mean "out of the plant, not yet finished" (`salio_planta`/`en_camino`/`proximo_llegar`/`en_obra`/`descargando`), then polls each one's `rutaRemision` every 15s the same way, rendering every truck's marker/trail together on one `GoogleMapsMapView` instead of one map per remisión.
- **`deliveries/`** — `DeliveriesScreen` ("Mis entregas del día") supports pull-to-refresh (`RefreshIndicator`, same pattern as `direccion/AutorizacionesScreen`) — its `FutureBuilder` always returns a `ListView` regardless of loading/error/success state (never a bare `Center`), since `RefreshIndicator` needs a scrollable descendant present in every state for the pull gesture to attach to. It's real, built by `entregas_service.dart`'s `EntregasService.entregasDelDia()`, which chains three independent services with no shared knowledge of each other: `operaciones`'s `GET /programacion-produccion?fecha=` (the *whole plant's* schedule for the given day, not per-driver — `HistorialEntregasScreen` reuses the same call with a past date the conductor picks, since it takes an arbitrary `fecha`) → `operaciones`'s `GET /remisiones?pedidoId=` (filtered client-side to keep only rows where `conductorId == AuthService.idEmpleado`, on the assumption that `auth-service`'s `idEmpleado` and `operaciones-service`'s `conductorId` share the same id space — unverified, flagged in code; a pedido with no remisión yet is skipped entirely, since there's nothing on it yet to say whose delivery it is) → `comercial`'s `obtenerPedido`/`obtenerObra`/`contactoParaEntrega` for job-site details, lat/lng, and the resolved `ClienteContacto` for this pedido's obra+cliente pairing (`Remision.contactoNombre`/`contactoCargo`/`telefono` carry it through to `widgets/contacto_card.dart`'s shared `ContactoCard`, a standalone card between `SummaryCard` and "Avanzar hito de entrega" — same widget `direccion/PedidoDetailScreen` uses — that only mounts once `contactoNombre` is non-empty). `EntregasService`'s `OperacionesService.remisionesPorPedido` lookup (same call `direccion/PedidoDetailScreen` uses) is what determines a pedido is this conductor's in the first place (see above) — `Remision.remisionId`/`hitoActual` are set from that same real `RemisionResumen.estatus`/`id`, and `Remision.volumenM3` becomes that remisión's own `metrosCargados`/`metrosSolicitados` rather than the pedido's total — a pedido can be split across several remisiones (e.g. 40 m³ as 4 trucks of 10 m³), each driver only sees their own truck's volume. The pedido-wide "solicitados/entregados/pendientes" line `SummaryCard` shows for context comes straight from `Pedido.volumenSolicitadoM3`/`volumenEntregadoM3`/`volumenPendienteM3` (`Remision.volumenPedidoTotal`/`volumenPedidoEntregado`/`volumenPedidoPendiente`), always available since the pedido is always fetched — deliberately *not* `RemisionResumen.metrosAcumuladosPedido`/`metrosPendientesPedido` (a remisión-derived echo of the same pedido totals, null until a Remisión exists, and previously mislabeled in this exact spot — see git history), since the pedido's own fields are simpler and don't depend on remisión data existing yet; **the app never creates a Remisión itself** (would need fields like `metrosCargados` the driver's phone has no way to know), so no Remisión yet means the pedido doesn't show up in "Mis entregas del día" at all rather than showing with a placeholder state. Once a Remisión exists, `DeliveryDetailScreen`'s stepper walks `HitoEntrega`'s 7-step sequence (`cargandoPlanta` → `salioPlanta` → `enCamino` → `proximoLlegar` → `enObra` → `descargando` → `entregado`, excluding the non-sequential `conIncidencia`) by calling the real `OperacionesService.avanzarHito`, which returns the updated `RemisionResumen` as the source of truth (server-stamped `hora*` timestamp) rather than an optimistic local guess; requires `permisoOperarRemisiones`. From `enObra` onward, `DeliveryDetailScreen` also exposes `PruebaConcretoScreen` (Operador de Bomba only, only once a Remisión exists) — a real `POST /pruebas-concreto-fresco` field test (revenimiento/masa unitaria/temperatura/rendimiento), client-stamped with the submission moment since it's a field test performed at delivery time. `DeliveryDetailScreen`'s firma/evidencia rows (below) stay visible but render via `ActionRow`'s `enabled` flag (dimmed colors, `onTap` swapped to `null` so `InkWell` no-ops) until `_hitoAlcanzado(detalle, HitoEntrega.descargando)` — signing off or attaching evidence before the truck has actually reached "Descargando" would let a driver confirm a delivery that hasn't happened yet, so both rows sit there disabled rather than disappearing (a driver should be able to see the action exists, just not use it yet), becoming enabled together once that hito is reached (checked against the same `_detalleFuture`/`_detalleOverride` the hito stepper itself uses, so advancing the hito enables them immediately without waiting on a refetch). Both rows only render at all (enabled or not) once a Remisión exists and the session holds `permisoOperarRemisiones` — without either, there's nothing to operate on, so they're hidden outright rather than shown disabled. `DeliveryDetailScreen` → `SignatureScreen` is now real too (Operador de Bomba/Olla, only once a Remisión exists and the session holds `permisoOperarRemisiones`, same gate as `PruebaConcretoScreen`): it renders the on-canvas signature pad to a PNG, requests a presigned upload URL from `operaciones`'s `POST /evidencias/presigned-url`, `PUT`s the bytes directly to that URL (straight to storage, bypassing the backend entirely — deliberately skips `AuthService.authHeaders`), then calls `OperacionesService.registrarFirma` (`POST /remisiones/{id}/firma`) with the returned `publicUrl`. `FirmaRequest.operadorId` would be the id of whoever receives at the job site (not the driver), but this app has no lookup against `administracion-service` to resolve a name to that id, and the field isn't schema-required — so it's omitted entirely; the driver's hand-typed name of who received goes in `comentarios` instead. Since `RemisionResponse` has no boolean "firmada" flag, `DeliveryDetailScreen` derives that status itself from `OperacionesService.firmasPorRemision` (`GET /remisiones/{id}/firma`) coming back non-empty, showing a green "Firmada" pill on the `ActionRow` (which now supports an optional `statusLabel`/`statusColor`, plus the `enabled` flag mentioned above) and re-fetching after `SignatureScreen` pops with `true`. The backend now rejects a second firma on the same remisión (409, since it would double-count delivered volume onto the pedido — see `comercial_service.dart` above) — once `firmasPorRemision` shows one already exists, tapping the row opens `EvidenciaViewerScreen` on the existing `firmaDigitalUrl` instead of reopening `SignatureScreen`. Same idea for `DeliveryPhotoScreen`'s evidencia: once `archivosPorRemision` has entries, a horizontal strip of tappable thumbnails (`Image.network` with `cacheWidth` to keep decode cheap) renders below its `ActionRow`, each opening `EvidenciaViewerScreen`; the row itself still opens `DeliveryPhotoScreen` to add more, since (unlike firma) there's no backend limit on how many can be attached. `DeliveryPhotoScreen` is now real too, same mechanism as `SignatureScreen`: each picked photo (camera/gallery, via `image_picker`) gets uploaded through the presigned-URL round trip, then attached with `OperacionesService.agregarArchivo` (`POST /remisiones/{id}/archivos`, `tipoArchivo: 'foto_evidencia'`) — one call per photo, since that endpoint takes a single `archivoUrl` at a time. Its `ActionRow` shows a "N fotos" pill derived from `OperacionesService.archivosPorRemision` (`GET /remisiones/{id}/archivos`) the same way `SignatureScreen`'s does from firmas. Still mock: `DosificacionScreen` (Operador de Bomba only; mock submission, the backend's `InformePesadora` entity has no service/controller/DTO yet) / `route_navigation_screen.dart`'s `RouteNavigationScreen` (**real** turn-by-turn navigation via `google_navigation_flutter`, and also the *sender* half of live GPS tracking: once guidance starts, if `remision.remisionId != null` and the session holds `permisoOperarRemisiones`, it posts the driver's current position via `OperacionesService.enviarPosicion` every 15s — same cadence as the Dirección-side poll — until arrival or the screen closes; a failed ping is silently swallowed and retried on the next tick rather than interrupting navigation). This closes the loop with the Dirección-side live tracking above, whenever a Remisión already exists.
- **`vehicle/`** — now real, backed by `operaciones/vehiculo.dart` DTOs and `OperacionesService`. `vehicle/vehiculo_service.dart`'s `VehiculoService.miVehiculo()` resolves the driver's own unit by fetching the fleet-wide `GET /vehiculos` and keeping the one whose `conductorAsignadoId` matches `AuthService.idEmpleado` (same cross-service id assumption as `conductorId` above) — there's no backend concept of "mi vehículo" as a single call. `VehicleScreen` shows that unit's details plus a mantenimiento-activo banner (derived from `mantenimientosVehiculo`'s `estatus`, no dedicated "is under maintenance" field), then links to `VehicleDocumentsScreen` (real `documentosVehiculo`, read-only — uploading a new document isn't wired up, though the same presigned-upload mechanism used elsewhere in this app now could back it), `VehiclePendientesScreen` (real `pendientesVehiculo`, read-only list — resolving one is a workshop/dirección action not wired here), and `VehiclePendingScreen` (real `POST /vehiculos/{id}/pendientes` to report a falla mecánica/llanta/mantenimiento/otro; requires `permisoReportarPendienteVehiculo`; the backend request has no `urgencia` field, so that selector was deliberately dropped rather than collecting input the server would discard). `VehiclePendingScreen` also supports an optional photo taken with the camera (`image_picker`): unlike `RemisionFirma`, `VehiculoPendiente` has no separate photo table — the same presigned-upload round trip (`operaciones`'s `POST /evidencias/presigned-url` + direct `PUT` to storage) just feeds its resulting `publicUrl` into `evidenciaApertura`, a plain field on the same pendiente row created by that same `POST`. There's a symmetric `evidenciaCierre` for whoever resolves the pendiente (`PATCH /pendientes-vehiculos/{id}/resolver`), but resolving isn't wired into this app at all (`VehiclePendientesScreen` stays read-only, see above). Both URLs are surfaced via a dedicated `VehiclePendienteDetailScreen` (tapping a `PendienteCard`, which now just shows a small camera-icon hint when evidence exists rather than cramming thumbnails into the list) — full descripción/fechas plus each evidencia photo shown full-width (`Image.network`, since they're already-public R2 URLs, no auth headers needed), tappable to open `EvidenciaViewerScreen`, a simple full-screen `InteractiveViewer` for pinch-to-zoom. `vehicle.dart` also derives document-expiry status (`vigente`/`porVencer`/`vencido`) client-side from a document's real `vigencia` date.
- **`administracion/administracion_service.dart`** (`AdministracionService`) — talks to the real `administracion` sandbox (`https://fnconcretos.app/sandbox/administracion`), same `AuthService.authHeaders()` bearer pattern as the other services. HR employee records: `GET /empleados/{id}` (`EmpleadoResponse`, kept as a full DTO with every field the backend returns, not just what this app displays) backs `ProfileScreen`'s fuller identity data (nombreCompleto/puesto/área/teléfono) that `/auth/me` doesn't have. Profile photo upload reuses the presigned-URL-then-`PUT` mechanism (its own `/evidencias/presigned-url` endpoint, not `operaciones`'s), then calls `actualizarFotoPerfil`, which does a full `PUT /empleados/{id}` round-tripping the just-fetched record's other fields since that endpoint replaces the whole row (no partial PATCH).
- **`profile/`** — mixed: `MfaScreen`, `ChangePasswordScreen`, and `ProfileScreen`'s core identity fields (usuario/cargo/correo, from `AuthService.username`/`rol`/`correo`, populated via the real `/auth/me`) make real `AuthService` calls; the fuller identity fields and photo come from `AdministracionService` above. Planta/ciudad (and the `EditProfileScreen` that edited them) were removed — `/auth/me` never returned them, so there was no real data to show or edit; don't reintroduce them without a backend source. The dark-mode toggle writes `themeNotifier`; "Cerrar sesión" does a real `AuthService.logout()` before navigating back to `LoginScreen`.

## Conventions to note

- UI copy (anything the user sees on screen) is in Spanish. Code — folder/file names, class/variable names, and comments — is in English. Don't mix the two the wrong way.
- Brand color is yellow, `AppColors.accent` (`lib/theme/app_colors.dart`, literal `Color(0xFFFFCC00)`). For accents (icons, highlights, active-nav-item circle), always use `AppColors.accent` rather than reading `colorScheme.primary` — Material3's tonal palette generation shifts the seed into a duller, less saturated yellow for the `primary` role. This was called out explicitly after `colorScheme.primary` crept into `profile_screen.dart` and the now-removed `placeholder_content.dart`; screens used to each hardcode the literal locally (and a couple drifted to a slightly different one) until `AppColors` consolidated it.
- Theme-aware card surfaces (e.g. `profile_screen.dart`'s settings cards) avoid the seed-derived `colorScheme.surfaceContainerHighest` (skews yellow on this app's yellow-seeded `ColorScheme` — rejected explicitly). Pattern instead: dark mode solid near-black `Color(0xFF141414)` with a light border; light mode white with a black-ish border (a black fill reads as a stray error state on a light background); text/icon colors computed per-theme to match since the card color isn't sourced from `Theme.of(context)` directly. This pattern recurs across `deliveries/`, `vehicle/`, and `direccion/` screens, not just `profile/` — `AppColors.card`/`surfaceAlt`/`border`/`text`/`mutedText` (all take `BuildContext`) and `widgets/field_group.dart`'s `FieldGroup` container now centralize it; prefer those over a fresh local `isDark ? ... : ...` ternary.
- Logo image (`assets/images/logo.png`) is expected to exist; screens fall back to an icon via `errorBuilder` if missing. `background.png` is unused — `LoginScreen`'s background is now the pure-`CustomPainter` `LoginBackground` widget (`lib/models/login_background.dart`, an animated drifting grid/dots effect), not an image asset. The splash screen instead depends on `assets/video/splash.mp4` (`video_player`) — its background color, `Color(0xFF15181B)`, must stay in sync with the native launch screens (`android/app/.../drawable/launch_background.xml`, `ios/Runner/Base.lproj/LaunchScreen.storyboard`) so there's no visible flash before the video's first frame.
- Network calls throughout `auth_service.dart`/`comercial_service.dart`/`operaciones_service.dart`/`administracion_service.dart` swallow transport errors into a generic `AuthException('No se pudo conectar con el servidor')` rather than surfacing raw exceptions — follow that pattern for any new service call so error handling stays consistent.
- Prefer `AppSnack.success`/`.error`/`.info` (`lib/widgets/app_feedback.dart`) over a raw `ScaffoldMessenger`/`SnackBar` call for user-facing feedback — it matches the app's themed card styling instead of Material's default grey bar.
