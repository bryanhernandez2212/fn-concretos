# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"FN Concretera" — a Flutter app for a concrete company. Note the package name in `pubspec.yaml` is `fn_concretos`, even though the directory/repo is `my_flutter_app`.

The app has grown from a UI-only prototype into a role-scoped mobile client with real backend calls for auth and for one office workflow (credit authorization), plus several feature areas that are still mock/local state. There's no single "the app does X" description — which parts are real vs. mocked varies screen by screen (see Architecture below), so check the specific screen before assuming either way.

## Commands

- Install dependencies: `flutter pub get`
- Run the app (choose a connected device/simulator): `flutter run`
- Static analysis (uses `flutter_lints` via `analysis_options.yaml`): `flutter analyze`
- Format code: `dart format .`
- Run tests: `flutter test` (there are currently no test files in the project)
- Build platform targets as needed: `flutter build apk`, `flutter build ios`, `flutter build macos`, `flutter build web`, etc.

There is no CI config and no custom build scripts — this is a stock `flutter create` project structure. Native Android/iOS projects require a Google Cloud API key with "Maps SDK" and "Navigation SDK" enabled (see `route_navigation_screen.dart` below) — without it the map loads blank/greyed out and in-app turn-by-turn errors out; the Navigation SDK is billed separately from the Maps SDK. `local_auth` (Face ID/Touch ID, see `auth/biometric_service.dart` below) needed two native changes to work at all: `MainActivity.kt` now extends `FlutterFragmentActivity` instead of `FlutterActivity` (the plugin's Android biometric prompt requires a `FragmentActivity` host), and `ios/Runner/Info.plist` has `NSFaceIDUsageDescription`. Known gap: Android's `styles.xml` `LaunchTheme`/`NormalTheme` still parent off plain `@android:style/Theme.*`, not an `AppCompat`/`Theme.DayNight` theme — the plugin's README warns this can crash the biometric dialog on Android 8 and below; not fixed here since it'd mean migrating the whole app's native theme, out of scope for what was asked (this app's `minSdk` is 24, so that risk window is Android 7.0–8.1 devices specifically). Android's `applicationId`/`namespace` (`android/app/build.gradle.kts`) is `com.fnconcretos.app`, matching the package the backend team registered in Firebase for OneSignal push (below) — it was still the untouched `flutter create` default (`com.example.my_flutter_app`) until that; `MainActivity.kt` lives at the matching `android/app/src/main/kotlin/com/fnconcretos/app/` path. iOS's bundle id hasn't been touched — OneSignal is Android-only in this app for now (see below), so nothing there forced it.

## Architecture

`lib/` is organized by feature folder, each holding its screen(s) plus any content specific to that screen; `lib/widgets/` holds components shared across features — `bottom_nav_bar.dart` (below), `evidencia_viewer_screen.dart` (`EvidenciaViewerScreen`, the pinch-to-zoom full-screen photo viewer, now shared by `vehicle/`, `deliveries/`, and `profile/`), `app_feedback.dart` (`AppSnack` — themed success/error/info snackbar, replacing plain `ScaffoldMessenger`/`SnackBar` calls), `field_group.dart` (`FieldGroup`, the rounded card container for grouping form fields), `info_pill.dart` (`InfoPill`, the small icon+label chip used on list cards), `whatsapp_button.dart` (`WhatsappButton`/`abrirWhatsApp`, opens a `wa.me` deep link for a contacto's teléfono; its icon is `font_awesome_flutter`'s `FontAwesomeIcons.whatsapp` — the only place in the app pulling in a third-party icon font instead of Material Icons, since the WhatsApp brand glyph isn't one), and `contacto_card.dart` (`ContactoCard`, shows a resolved `ClienteContacto`'s nombre/cargo/teléfono plus a `WhatsappButton`, shared by `direccion/PedidoDetailScreen` and `deliveries/DeliveryDetailScreen`). `lib/theme/app_colors.dart`'s `AppColors` is the single source of truth for brand/status colors and the theme-aware card-surface/text helpers described under Conventions below — it replaced dozens of screens each redeclaring their own local color constants, which had already drifted into inconsistent literals in a few places; import it rather than adding a new local constant. Screens navigate via `Navigator.push`/`pushReplacement` with `MaterialPageRoute` — there is no named-route table or router package, and no state-management package (no Provider/Riverpod/Bloc) — each screen manages its own local `State`. `main.dart`'s `themeNotifier` (a top-level `ValueNotifier<ThemeMode>`, default `ThemeMode.dark`, that `MaterialApp` listens to) and `AuthService`'s static session fields are the only pieces of state shared across screens; both use the same "static field, no package" pattern rather than introducing one.

**Navigation is role/permission-branched, not a single fixed flow.** `main.dart` → `SplashScreen` (plays `assets/video/splash.mp4` via `video_player` to completion, or falls straight through on load failure — while it plays, `AuthService.restoreSession()` runs in parallel off a persisted refresh token so the network round trip isn't extra wait time on top of playback) → either `LoginScreen` or straight to the post-login destination, via the shared `destinationForSession()` helper (`auth/login_screen.dart`), then routed by role/permission:
- Role name in `roles.dart`'s `rolesConAppMovil` (`Operador de Olla`, `Operador de Bomba`) → `home/HomeScreen` (field-ops shell: Entregas/Vehículo/Perfil tabs).
- Otherwise, holding the `pedidos.autorizar_credito` permission → `direccion/DireccionHomeScreen` (Autorizaciones/Rutas/Perfil tabs).
- Otherwise, holding the `agenda.administrar` permission → `asesor_comercial/AsesorComercialHomeScreen` (Visitas/Cotizaciones/Perfil tabs).
- Anyone else → `auth/RoleUnavailableScreen` (explains the role has no mobile screens yet, points to the desktop system, offers logout).

All three shells reuse the same tab pattern: all tabs stay mounted and are cross-faded (`AnimatedOpacity` + `AnimatedScale`, not `IndexedStack`) so tab state survives switching, with a floating `widgets/bottom_nav_bar.dart` (`BottomNavBar`, icon-only pill nav, active item gets a solid accent-colored circle; exposes `BottomNavBar.clearance(context)` for scrollable screens to pad their bottom content).

Dirección's and Asesor Comercial's routing is deliberately by *permission*, not role name, per a comment in `direccion/comercial_service.dart`: the backend's roles-controller can reassign permissions to a different/renamed role independently of this app, so hardcoding a role-name check would silently break if that happens. `auth/roles.dart` keeps a static `catalogoRoles` mirroring the backend's `/roles` catalog purely so screens can show a role's Spanish name/description without a network round trip.

### Real backend calls vs. mock data — check per screen

All backend base URLs live in one place, `lib/config/api_config.dart`'s `ApiConfig` — each is `$_host/<service>` off one shared sandbox host (`auth`/`comercial`/`operaciones`/`administracion`/`catalogo`), so switching environments (or adding a service) means touching this one file rather than a literal repeated across services, as it used to be. `.env` used to be tracked too, empty and unused; it's gitignored now instead.

- **`auth/auth_service.dart`** (`AuthService`) — talks to the real `auth-service` sandbox (`ApiConfig.auth`, see its `/v3/api-docs`). Session (access/refresh tokens, `username`, `rol`, `permisos`, `mfaHabilitado`, `idEmpleado`) lives in static fields, refreshed transparently before each authenticated call (`_ensureFreshToken`). The refresh token is also persisted via `flutter_secure_storage`, so `restoreSession()` (called from `SplashScreen`) can log the user back in silently across app restarts without re-prompting for credentials; logout/refresh-failure clears the stored token. Covers login, MFA enroll/verify (TOTP), forgot/reset/change password, logout. `LoginScreen` handles `MfaRequiredException` with an in-place TOTP dialog. `POST /auth/validate` is deliberately unimplemented — it's an API Gateway/inter-service introspection endpoint, not something a mobile client calls. The API docs mark MFA enrollment as mandatory for Dirección/Pagos, but the backend doesn't block login over it; the app enforces that itself — `ProfileScreen`'s MFA tile shows real status from `mfaHabilitado`, and `direccion/DireccionHomeScreen` shows a one-time-per-session dialog nudging enrollment when `mfaHabilitado == false` (deliberately dismissible with "Más tarde" rather than a hard lock, since there's no confirmed backend-side enforcement to mirror). Pagos isn't affected — it has no mobile screens at all (not in `rolesConAppMovil`), so it never reaches a screen where this could be enforced. **Face ID/Touch ID quick login is a local device gate, not a backend factor**: `AuthService.biometricHabilitado` (persisted via `flutter_secure_storage`, toggled from `ProfileScreen`'s "Seguridad" group, only shown when `auth/biometric_service.dart`'s `BiometricService.disponible()` says the device supports it) gates whether `SplashScreen` routes a restored session through `auth/biometric_lock_screen.dart`'s `BiometricLockScreen` before letting it into the app. Enabling it (`AuthService.habilitarBiometria()`) implicitly turns on refresh-token persistence too, even if "Recordar sesión" wasn't checked at login — otherwise there'd be nothing for Face ID to unlock next launch. There is no backend concept of biometric auth; this never touches `auth-service`, it only decides whether *this device* recognizes whoever is holding it before handing over an already-restored session — don't confuse it with MFA above, which the backend does know about.
- **`direccion/comercial_service.dart`** (`ComercialService`) — talks to the real `comercial` sandbox (`ApiConfig.comercial`), reusing `AuthService.authHeaders()` for bearer auth. `obtenerCliente`/`obtenerObra`/`estadoCuenta`/`clientesPorObra`/`contactosCliente` go through a private `_cached` helper (a `Map<String, (dynamic, DateTime)>` static field, 60s TTL) — added after `PedidoDetailScreen` felt slow to re-open, since each `Navigator.push` into it is a brand-new screen instance that re-fetches all of this from scratch even for a pedido already viewed that session. Deliberately *not* applied to `pedidosPendientesDePago` (the authorization queue itself — a stale read could hide/show a pedido someone else just actioned), `obtenerPedido` (kept live-polled, see below), or any write call. This is the one place in the app that caches HTTP responses at all — everywhere else still fetches fresh per the "no state-management package" convention (see Architecture above); this stays a plain static field rather than a package for the same reason. Backs `AutorizacionesScreen` (live list of pedidos pending credit authorization) and `PedidoDetailScreen` (cliente + estado de cuenta lookup, aprobar/rechazar). A `Cliente` has no phone of its own — contact info lives on its named `ClienteContacto`s (`GET /clientes/{id}/contactos`; a cliente can have several, e.g. "Residente de obra" vs. "Compras"), and *which* contacto is the right one for a given pedido depends on the obra: `GET /obras/{obraId}/clientes` returns that obra's cliente↔contacto pairings (an obra can have more than one cliente tied to it, e.g. shared job sites), each optionally naming a `contactoId`. `ComercialService.contactoParaEntrega({obraId, clienteId})` does both lookups and returns the resolved `ClienteContacto?` — null if no contacto is assigned for that pairing. `widgets/contacto_card.dart`'s shared `ContactoCard` renders it (nombre/cargo/telefono) plus a WhatsApp button when `telefono != null`, on both `PedidoDetailScreen` and `deliveries/DeliveryDetailScreen` (see `deliveries/` below) — the button itself is `widgets/whatsapp_button.dart`'s `WhatsappButton`, which opens a `https://wa.me/` deep link (via `url_launcher`) with Mexico's `52` country code prefixed onto the backend's plain 10-digit `telefono`. `EstadoCuenta.disponible == false` means the estado-de-cuenta call is answering from a stub, not real account data — surface that distinction, don't treat a stubbed response as a real "cliente al corriente". `pedido.dart` also holds `Obra` (`obtenerObra`) — a pedido's job site, with the lat/lng used for maps/navigation. `Pedido.volumenEntregadoM3`/`volumenPendienteM3`/`estatusGeneral` (`'parcial'`/`'completo'`) now update for real as each remisión gets firmada — `operaciones-service`'s `RemisionService.registrarFirma` calls an internal `comercial-service` endpoint (`PATCH /pedidos/{id}/registrar-entrega`, not in the public API docs, not called by this app directly) that accumulates delivered volume and recalculates status server-side. `PedidoDetailScreen`'s `SummaryCard` shows this as a progress bar once any volume has been delivered. Since a pedido's remisiones can be firmadas from a different conductor's device — nothing local would otherwise trigger a refetch — `PedidoDetailScreen` re-polls `obtenerPedido` every 15s (same cadence as its "Ubicación en vivo" polling below) to keep those totals current, separately from `deliveries/DeliveryDetailScreen`'s own one-shot refresh described below.
- **`asesor_comercial/`** — a third role, real from the start (confirmed against `comercial-service`'s live `/v3/api-docs` before building, not assumed): `asesor_comercial_service.dart`'s `AsesorComercialService` talks to the same `comercial` sandbox `direccion/comercial_service.dart` does, for a disjoint set of entities (`AsesorComercial`/`VisitaObra`/`Cotizacion`/`SolicitudDisenoEspecial`) that Dirección never touches — kept as its own service/folder rather than added onto `ComercialService`, matching how `operaciones_service.dart` and `comercial_service.dart` are already separate services on the same app despite occasional cross-feature reuse. `AsesorComercialService.miAsesor()` resolves the logged-in advisor's own `Asesor` row the same way `vehicle/vehiculo_service.dart`'s `miVehiculo()` does — fetching the unfiltered `GET /asesores` and matching client-side — but against `AsesorResponse.usuarioId` (the `/auth/me` *account* id), not `idEmpleado`, since that's the field this particular backend record links by (same `usuarioId`-vs-`idEmpleado` distinction the notifications section below calls out). Three permission constants gate this role's write calls the same inline way `OperacionesService`'s `permisoOperarRemisiones` does (checked by the caller, not the service method): `permisoAdministrarAgenda` (`'agenda.administrar'` — the only place this app still checks it is `destinationForSession()`'s routing, see Navigation above; there used to be an Agenda tab/screen gated by it too, dropped since it had nothing to do — see below), `permisoAplicarDescuentoEspecial` (`'cotizaciones.aplicar_descuento_especial'`, shows/hides the `porcentajeDescuento` field on `CotizacionFormScreen`), and `permisoAdministrarPreciosCatalogo` (`'catalogo.precios.administrar'`, not yet exercised by any screen — no catalog-pricing UI exists in this build). Screens: `VisitasScreen` (date-pill pattern copied from `deliveries/historial_entregas_screen.dart`, plus a `visitas/resumen-dia` summary card — its date picker's `lastDate` reaches 90 days into the future, not just today, now that "Programar visita" below can put a Visita on a date this list needs to be able to browse forward to) → `VisitaDetailScreen` (`Visita` itself carries no dirección, only `obraNombre` — so this screen makes its own best-effort `ComercialService.obtenerObra(obraId)` call to show one; a failed lookup just means that card doesn't render, not a broken screen. `Obra` gained nullable `ciudad`/`colonia` fields for this — previously unmapped even though `crearObra`'s request already sent them — so the shown address can be more than just the raw `direccion` string. The location itself renders as a static map "thumbnail" — a gesture-disabled `GoogleMapsMapView` wrapped in `IgnorePointer` (the native platform view otherwise still eats the tap even with its own gestures disabled, same reasoning as `pedido_detail_widgets.dart`'s embedded tracking cards) so the surrounding `InkWell` reliably catches the tap — that opens `ObraLocationViewScreen`, a fullscreen *interactive* (pan/zoom) but still read-only map, entirely in-app; there's deliberately no "abrir en Google Maps" external hand-off, an earlier version had one and it was explicitly rejected in favor of staying in-app) → `VisitaCheckinScreen` (one-shot `geolocator` position + optional camera photo) and `CotizacionesScreen` (estatus-filtered, client-side-narrowed to this advisor's own `asesorId` since `GET /cotizaciones` has no such filter, plus a header "+" opening `CotizacionFormScreen` standalone — the web app allows creating a cotización without a visita too, so this isn't `VisitaDetailScreen`-only the way obra/visita creation is) → `CotizacionDetailScreen` (marcar lista/cancelar/duplicar/convertir-a-pedido, plus editar — an app-bar pencil icon reopening `CotizacionFormScreen` pre-filled from the existing `Cotizacion`, hidden once `estatus == 'convertida'` since a converted cotización is done). `CotizacionFormScreen` also opens from a `VisitaDetailScreen` with clienteId/obraId prefilled and read-only (`origenFijo`); a cotización now holds one-or-more línea items (`CotizacionItem`/`productos`, `CotizacionRequest.productos` requires at least one) rather than a single product/volumen/precio — each línea's `tipoLinea` is `producto` (needs `productoId`+`volumenM3`, picked from `catalogo/catalogo_service.dart`'s real `catalogo-service` catalog, a fifth backend sandbox this app hadn't talked to before — see below), `bombeo` (no `productoId`, `volumenM3` optional since the backend autofills it as the sum of the cotización's `producto` líneas), or `servicio` (flat `precioUnitario`, e.g. lavado/flete manual); `flete_vacio` is a fourth línea the backend generates itself (one per `producto` línea whose volumen doesn't divide evenly into the planta's `capacidadReferenciaM3`) and this app never sends one — `CotizacionFormScreen`'s summary card only previews that charge client-side from the selected `Planta`'s `capacidadReferenciaM3`/`precioPorM3Vacio`, the backend's own recalculation on save is authoritative. `plantaId` (required to submit) resolves from, in order: the obra's own `plantaId` (`Obra` gained this field for exactly this) if one was picked/prefilled, else the logged-in advisor's own `Asesor.plantaId`, else a manual dropdown/fallback text field. Discount (`porcentajeDescuento`) is never hidden behind `permisoAplicarDescuentoEspecial` client-side — the form always shows it, since anyone can request up to the backend's own per-forma-de-pago limit (`cotizacion.dart`'s `limiteDescuentoTexto`, shown as a hint, not enforced client-side) and only exceeding that limit needs the permission, checked server-side. Editing (`AsesorComercialService.actualizarCotizacion`, `PUT /cotizaciones/{id}`, "solo mientras no esté convertida a pedido") resends the whole cotización body the same shape as creating one — no partial PATCH, same pattern as `AdministracionService.actualizarFotoPerfil`. `CotizacionDetailScreen` shows each partida's breakdown (tipoLinea/volumen/precio unitario/precio total) and best-effort resolves `productoId`→nombre and `contactoId`→nombre against the same catalogs (a failed lookup just shows the raw id/tipoLinea instead, not a broken screen). `VisitaDetailScreen` also exposes `solicitud_diseno_screen.dart`'s `SolicitudDisenoScreen` (`AsesorComercialService.crearSolicitudDiseno`, `POST /solicitudes-diseno` — producto/revenimiento/tamaño de agregado/característica especial/fecha deseada, all optional; clienteId/obraId prefilled from the visita) for when an obra needs a special mix design filed before quoting; resolving viabilidad is a laboratorio-side action this app doesn't expose, so the screen only creates the request and pops back — same "create only, no follow-up UI" shape as `crearObra`/`crearCliente` above. There used to be a fourth "Agenda" tab (`AgendaScreen`, backed by `AgendaActividad`/`GET /agenda/ruta-diaria`/`pendientes-vencidas`) — removed, since it was a dead end: no screen ever called the `POST /agenda` create endpoint (`crearActividad` existed in `AsesorComercialService` but nothing wired it to any UI), so the tab only ever listed/marked-complete activities that nothing in this app ever populated. `Visita` scheduling (below) now covers the "what am I doing today/next" need this role actually has, so Agenda wasn't replaced with anything — just gone. Advisors register their own clientes and obras in the field — they don't necessarily have any Visita scheduled to hang that off of ("agregar obra" was deliberately built to *not* depend on one, after an earlier version gated it inside `VisitaDetailScreen` and turned out to have that backwards) — so `VisitasScreen` has a single "+" header button (`_mostrarOpciones`, next to the `NotificationBellButton`, independent of the date-scoped Visita list below it) opening a labeled action sheet with "Registrar visita" and "Agregar obra" — two adjacent icon-only buttons were tried first and turned out to read as one ambiguous blob, so a bottom sheet with subtitles replaced them. "Agregar obra" starts: `ClientePickerScreen` (`ComercialService.buscarClientes`, `GET /clientes?q=`, free-text against nombre/numeroCliente — plus a "Registrar cliente nuevo" action opening `ClienteFormScreen`, `POST /clientes`, since the cliente itself may not be in the system either) resolves the `Cliente` that will own the obra, since `POST /obras` requires a `clientePrincipalId`; picking or creating one hands off straight to `ObraFormScreen` (`ComercialService.crearObra`, `POST /obras` — nombre/clientePrincipalId/latitud/longitud required in this app even though the backend schema also lists direccion/ciudad/colonia/googleMapsLink as optional companions). Both `crearObra` and the new `buscarClientes`/`crearCliente` live in `direccion/comercial_service.dart` alongside `obtenerObra`/`obtenerCliente` rather than in `asesor_comercial_service.dart`, since they're squarely `obra-controller`/`cliente-controller` domain — Asesor Comercial's screens just reach into that service the same way `deliveries/EntregasService` already does. Unlike `VisitaCheckinScreen`'s one-shot `Geolocator.getCurrentPosition()` (fine for "where is the advisor standing right now"), an obra's latitud/longitud have to be its exact spot, since they're what `route_navigation_screen.dart`'s turn-by-turn navigation sends conductores to later — a device-current-position guess isn't precise enough on its own. So `ObraFormScreen`'s location field opens `ObraLocationPickerScreen`, a full-screen *interactive* `GoogleMapsMapView` (gestures left on, unlike the read-only/gesture-disabled ones used for live tracking) that starts centered on the device's current position but lets the advisor pan/zoom/tap to drop the pin exactly where the obra is — the in-app equivalent of dropping a pin in the Google Maps app. Once a pin is picked, `ObraFormScreen` auto-fills direccion/ciudad/colonia (only the fields still empty, so it never overwrites something the advisor already typed) via the `geocoding` package's `Placemark.street`/`locality`/`subLocality` — a **native OS reverse-geocode** (`CLGeocoder`/Android `Geocoder`), deliberately not a Google Maps Geocoding API call, since that would need yet another Cloud API enabled on top of the Maps/Navigation SDK gap already tracked; best-effort, a failed lookup just leaves those fields for the advisor to type. `googleMapsLink` is regenerated from the pin every time (`https://www.google.com/maps/search/?api=1&query=lat,lng`), since it's meant to always mirror the current pin rather than be independent input. Both `crearCliente`/`crearObra` only create their respective record — there's no Visita to attach anything back onto — but once the obra exists, `ObraFormScreen` hands off to `VisitaFormScreen` (`AsesorComercialService.crearVisita`, `POST /visitas`, "Asignar una visita a obra a un asesor" — asesorId/obraId/clienteId/fechaVisita required, zonaId/contactoNombre/contactoTelefono/volumenAproximado optional; `asesorId` resolved via `miAsesor()`, `obraId`/`clienteId` prefilled from the obra/cliente just created), since the advisor is usually standing at the site they just registered and logging the visita is the near-certain next step. This is the only way this app creates a Visita — `visitasDelDia`/`VisitasScreen` otherwise only ever lists ones that already exist. Skippable: `VisitaFormScreen`'s back arrow pops without creating one, since registering the obra alone is still a complete, valid action. "Registrar visita" (the same action sheet's other option) is for the repeat-visit case — a cliente/obra the advisor has already registered, so re-running the whole obra-registration flow would be pointless. It reuses `ClientePickerScreen` for the cliente, then `ObraPickerScreen` (`ComercialService.buscarObras`, `GET /obras?nombre=`) to find the existing obra — that screen's own "Registrar obra nueva" falls through to `ObraFormScreen` for the case the obra actually doesn't exist yet either, and since `ObraFormScreen` already handles the whole rest of the chain (crear obra → `VisitaFormScreen`) and pops everything itself, `ObraPickerScreen` just pops with `null` in that branch rather than an `Obra` — `VisitasScreen._registrarVisita` only opens `VisitaFormScreen` itself when an *existing* obra was picked. `POST /visitas` only *asigna* the visita (estatus starts `asignada`) — it isn't proof anyone actually showed up, that's what the separate, geolocated `POST /visitas/{id}/checkin` is for. `VisitaFormScreen` surfaces that as an explicit up-front choice rather than inferring it from the date picked (`ChoiceChip` pair, "Visita al instante" vs "Programar visita" — the latter locks in until deliberately switched back): instantánea locks `fechaVisita` to today and, right after `crearVisita` succeeds, chains straight into `VisitaCheckinScreen` (the advisor is standing there that moment, so finding the new visita in the list and checking in as a separate trip through the UI would be a strange detour); programada opens the date picker for a future date and skips the check-in chain entirely, since there's nothing to geolocate for a visit that hasn't happened yet. Switching modes resets `fechaVisita` sensibly (today for instantánea, tomorrow for programada if it was still on today). **`comercial-service` has no presigned-upload endpoint of its own** — `VisitaCheckinRequest.fotoEvidenciaUrl` just expects an already-public URL — so the check-in photo deliberately reuses `OperacionesService.presignedUploadUrl`/`subirArchivoPresignado` (the **operaciones** sandbox) purely to get a public URL from the same storage bucket every other evidencia upload in this app already uses; this is the one place a comercial-facing screen calls across to the operaciones service. `convertirAPedido`'s response is parsed with the existing `Pedido` DTO from `direccion/pedido.dart` (same field names) rather than a new one, but on success the screen shows the folio in a snackbar and pops back to the list instead of opening `direccion/PedidoDetailScreen` — that screen's aprobar/rechazar actions are Dirección-only and shouldn't be shown to an Asesor Comercial.
- **`catalogo/catalogo_service.dart`** (`CatalogoService`) — talks to the real `catalogo` sandbox (`ApiConfig.catalogo`), a fifth microservice this app hadn't talked to before (`catalogo-service`, confirmed via its own live `/v3/api-docs`), same `AuthService.authHeaders()` bearer pattern as the other services. Only covers the read endpoints `CotizacionFormScreen`/`CotizacionDetailScreen` need (see `asesor_comercial/` above): `plantas()` (`GET /plantas`, returning `Planta`'s `capacidadReferenciaM3`/`precioPorM3Vacio` used for the flete_vacio preview), `productos({q})` (`GET /productos`, `q` free-text against nombre, same idiom as `ComercialService.buscarClientes`), and `preciosProducto(productoId, {plantaId})` (`GET /productos/{id}/precios` — a producto's precio can vary per planta) — not the rest of `catalogo-service` (materiales, insumos, empresas, zonas, seguros...), which backs desktop-only catalog administration this app doesn't expose.
- **`operaciones/operaciones_service.dart`** (`OperacionesService`) — talks to the real `operaciones` sandbox (`ApiConfig.operaciones`), same auth-header pattern as `ComercialService`. Lives in its own top-level folder (not under `direccion/`, despite originating there) because it's consumed by `direccion/`, `deliveries/`, and `vehicle/` — same reasoning as `auth_service.dart` living in `auth/` rather than any one screen's folder. Backs: `direccion/PedidoDetailScreen`'s "Ubicación en vivo" section (fetches the pedido's remisiones via `GET /remisiones?pedidoId=`, then polls `GET /remisiones/{id}/ruta` every 15s to render current position + trail on a `GoogleMapsMapView` — read-only map view from the same `google_navigation_flutter` package used for driving navigation, no extra dependency/API key needed; a pedido can have more than one remisión — e.g. olla and bomba, or several truck loads splitting one pedido's total volume — so this section renders one live-tracking card per remisión found, each showing that remisión's own conductor id and volume (`metrosCargados`/`metrosSolicitados` — not the pedido's total — no employee-name lookup exists in this app, so it's shown as a raw id rather than a fabricated name)); `deliveries/EntregasService` (below), via `programacion-produccion` and `remisiones`; `asignacionesPorPedido`/`AsignacionResumen` also live here (a real endpoint, `GET /asignaciones?pedidoId=`) but as of a bug fix are no longer called by `EntregasService` — it answers a different question than "which conductor owns this pedido" and can come back empty for a pedido that already has a remisión with a conductor on it (confirmed against real sandbox data: pedido 20 had an empty `/asignaciones` response despite an existing remisión with `conductorId` set), which was silently hiding otherwise-ready deliveries; the hito state machine (`avanzarHito`, `remisionDetalle`) and GPS reporting (`enviarPosicion`) also used by `deliveries/`; `pruebas-concreto-fresco` field tests; and the `vehiculos`/`mantenimientos`/`pendientes-vehiculos`/`documentos` family of endpoints backing `vehicle/` (below). Two module-level permission constants gate write calls: `permisoOperarRemisiones` (`'remisiones.operar'`, required for `enviarPosicion`/`avanzarHito`/`registrarPruebaConcreto`) and `permisoReportarPendienteVehiculo` (`'vehiculos.reportar_pendiente'`, required for `registrarPendienteVehiculo`). `remisionesEnRuta()` backs `direccion/RutasActivasScreen` ("Rutas" tab) — a fleet-wide consolidated map, not scoped to one pedido like "Ubicación en vivo" above: it calls `GET /remisiones` with no filter at all (both `pedidoId` and `estatus` are optional per the OpenAPI schema, same as the unfiltered `vehiculos()` call) and narrows client-side to the statuses that mean "out of the plant, not yet finished" (`salio_planta`/`en_camino`/`proximo_llegar`/`en_obra`/`descargando`), then polls each one's `rutaRemision` every 15s the same way, rendering every truck's marker/trail together on one `GoogleMapsMapView` instead of one map per remisión. Both this screen and `PedidoDetailScreen`'s "Ubicación en vivo" cards render each remisión as a rotating truck-shaped marker (`direccion/vehicle_marker_icon.dart`'s `VehicleMarkerIcon`, one `registerBitmapImage`-registered bitmap per route color, cached process-wide since that registry isn't scoped to one `GoogleMapViewController`) rather than the default static pin — heading comes from `bearingBetween()` on the last two `historial` points, since neither `RutaRemisionResponse` nor `GpsPingResponse` carries one from the backend, and is held over across polls with too little history rather than snapping back to north. `PedidoDetailScreen`'s per-remisión "Ubicación en vivo" cards (embedded and fullscreen, not `RutasActivasScreen`'s fleet-wide view) also overlay a DiDi-style speed readout, a right-edge vertical route-progress bar, and a bottom "llega en X min" ETA — `direccion/vehicle_marker_icon.dart`'s `speedKmhBetween()` (same "derive client-side from the last two `historial` points" idiom as `bearingBetween()`, using `Geolocator.distanceBetween` for the great-circle distance) covers speed with zero new dependencies, but progress/ETA need a real road-network distance, which a passive `GoogleMapsMapView` has no way to compute on its own (that's normally a Navigation-SDK-guidance-session feature tied to whoever's actively navigating — `deliveries/route_navigation_screen.dart`'s conductor-side screen — not something a remote viewer like Dirección watching an olla/bomba can read off the map). `direccion/directions_service.dart`'s `DirectionsService` calls Google's classic Directions API (a plain REST endpoint, not a native SDK) with the same Maps Platform key already embedded in `AndroidManifest.xml`/`AppDelegate.swift` — confirmed already enabled on the `fnconcretos` Cloud project in the same Console session that found Navigation SDK access missing (Directions API is a normal self-serve API, unlike Navigation SDK's gated approval; see [[navigation_sdk_access_gap]]). `direccion/route_eta.dart`'s `RouteEtaTracker` wraps that call per remisión, throttled to at most once every 60s regardless of the 15s GPS/position poll driving it (`_actualizarEta`, called via `unawaited()` so a slow/failed Directions call never blocks marker glide updates) — real routing calls are billed per request, so this stays deliberately coarser than position polling. Progress is computed against the *first* successful call's remaining distance (treated as the route's total), not a fixed original plan, so it'll drift if the truck deviates from Directions' suggested route — an accepted approximation, not a full route-matching/snap-to-road system. `RutasActivasScreen`'s fleet-wide view gets the same speed/ETA/progress data, but surfaced differently: since several trucks share one map, a single right-edge progress bar wouldn't have an obvious "whose truck" answer, so instead each truck's row in the bottom list panel shows its own "X km/h · Llega en Y min" line plus a thin `LinearProgressIndicator`, all colored to match that truck's route color. `RemisionResumen` (unlike `deliveries/remision.dart`'s driver-facing `Remision`) was never built with a destino already resolved, so it gained a `pedidoId` field (previously unmapped even though the raw response has it) purely so this screen can chain `obtenerPedido` → `obtenerObra` once per remisión (cached in a `Map<int, LatLng>`, not re-resolved every 15s poll) to get each truck's obra coordinates for its own `RouteEtaTracker`. `RutasActivasScreen` also has a "pantalla completa" toggle (AppBar action) that hides the bottom truck-list panel so the map fills the screen — implemented as a `Stack` where the map is always `Positioned.fill` and the list is the thing that's conditionally shown/hidden, specifically so toggling never tears down and recreates the native map view (which would lose camera position and force a marker rebuild). `PedidoDetailScreen`'s per-remisión tracking card is deliberately gesture-disabled (see below) and embedded in a scrolling list, so its fullscreen equivalent is a separate pushed screen (`LiveTrackingFullscreenScreen` in `pedido_detail_widgets.dart`) with its own independent poll/marker logic rather than a shared controller — the embedded card's map and the fullscreen one are distinct native platform views either way. `RutasActivasScreen` also shows `deliveries/deliveries_widgets.dart`'s `RutasResumenCard` above the map (hidden in pantalla completa) — the same asignadas/en ruta/entregadas/pendientes summary `DeliveriesScreen` shows a conductor for their own day, but fleet-wide: `deliveries/entregas_service.dart`'s `EntregasService.resumenFlotaDelDia()` walks the day's `programacion-produccion` and sums every pedido's remisiones (any conductor, not just the logged-in one) into a `ResumenEntregasDia`. It skips the per-pedido cliente/obra/contacto lookups `entregasDelDia()` needs for its detail cards, since a count only needs each remisión's `estatus` — and it's refreshed on its own 60s timer, separate from the map's 15s GPS poll, since it still costs one `/remisiones?pedidoId=` call per pedido programado hoy rather than the map's single unfiltered `/remisiones` call.
- **`deliveries/`** — `DeliveriesScreen` ("Mis entregas del día") supports pull-to-refresh (`RefreshIndicator`, same pattern as `direccion/AutorizacionesScreen`) — its `FutureBuilder` always returns a `ListView` regardless of loading/error/success state (never a bare `Center`), since `RefreshIndicator` needs a scrollable descendant present in every state for the pull gesture to attach to. Above the list, a dashboard header derives everything client-side from that same fetched `Remision` list (no extra calls): a counts row (asignadas/en ruta/entregadas/pendientes) and, when there's at least one pending remisión, a "Rutas prioritarias" preview of up to 3 (via `_ordenPorPrioridad` — remisiones with no resolved hito or flagged `conIncidencia` sort first, then by `horaProgramada`) with a "Ver todas" button opening `todas_rutas_screen.dart`'s `TodasLasRutasScreen` once there are more than 3 pending (a full same-day list, all hitos, that re-fetches its own copy via `EntregasService` rather than trusting a snapshot handed down, since it could already be stale by the time it's reached). When there's nothing to prioritize, that button instead routes to either "Ver todas las entregas de hoy" (everything today is already entregado) or "Ver próximas entregas" (nothing assigned today at all) opening `proximas_entregas_screen.dart`'s `ProximasEntregasScreen` — the forward-looking counterpart to `HistorialEntregasScreen`, same date-picker + `EntregasService.entregasDelDia(fecha:)` pattern but picking from tomorrow through 90 days out instead of before today. It's real, built by `entregas_service.dart`'s `EntregasService.entregasDelDia()`, which chains three independent services with no shared knowledge of each other: `operaciones`'s `GET /programacion-produccion?fecha=` (the *whole plant's* schedule for the given day, not per-driver — `HistorialEntregasScreen` reuses the same call with a past date the conductor picks, since it takes an arbitrary `fecha`) → `operaciones`'s `GET /remisiones?pedidoId=` (filtered client-side to keep only rows where `conductorId == AuthService.idEmpleado`, on the assumption that `auth-service`'s `idEmpleado` and `operaciones-service`'s `conductorId` share the same id space — unverified, flagged in code; a pedido with no remisión yet is skipped entirely, since there's nothing on it yet to say whose delivery it is) → `comercial`'s `obtenerPedido`/`obtenerObra`/`contactoParaEntrega` for job-site details, lat/lng, and the resolved `ClienteContacto` for this pedido's obra+cliente pairing (`Remision.contactoNombre`/`contactoCargo`/`telefono` carry it through to `widgets/contacto_card.dart`'s shared `ContactoCard`, a standalone card between `SummaryCard` and "Avanzar hito de entrega" — same widget `direccion/PedidoDetailScreen` uses — that only mounts once `contactoNombre` is non-empty). `EntregasService`'s `OperacionesService.remisionesPorPedido` lookup (same call `direccion/PedidoDetailScreen` uses) is what determines a pedido is this conductor's in the first place (see above) — `Remision.remisionId`/`hitoActual` are set from that same real `RemisionResumen.estatus`/`id`, and `Remision.volumenM3` becomes that remisión's own `metrosCargados`/`metrosSolicitados` rather than the pedido's total — a pedido can be split across several remisiones (e.g. 40 m³ as 4 trucks of 10 m³), each driver only sees their own truck's volume. The same conductor can also own more than one remisión on the same pedido (e.g. an olla making several trips because it can't carry the full volume in one load), so `entregasDelDia()` emits one `Remision` list entry per matching remisión rather than just `.first` — collapsing to one would let an already-entregada trip shadow a still-active one (or vice versa) depending on array order. The pedido-wide "solicitados/entregados/pendientes" line `SummaryCard` shows for context comes straight from `Pedido.volumenSolicitadoM3`/`volumenEntregadoM3`/`volumenPendienteM3` (`Remision.volumenPedidoTotal`/`volumenPedidoEntregado`/`volumenPedidoPendiente`), always available since the pedido is always fetched — deliberately *not* `RemisionResumen.metrosAcumuladosPedido`/`metrosPendientesPedido` (a remisión-derived echo of the same pedido totals, null until a Remisión exists, and previously mislabeled in this exact spot — see git history), since the pedido's own fields are simpler and don't depend on remisión data existing yet; **the app never creates a Remisión itself** (would need fields like `metrosCargados` the driver's phone has no way to know), so no Remisión yet means the pedido doesn't show up in "Mis entregas del día" at all rather than showing with a placeholder state. Once a Remisión exists, `DeliveryDetailScreen`'s stepper walks `HitoEntrega`'s 7-step sequence (`cargandoPlanta` → `salioPlanta` → `enCamino` → `proximoLlegar` → `enObra` → `descargando` → `entregado`, excluding the non-sequential `conIncidencia`) by calling the real `OperacionesService.avanzarHito`, which returns the updated `RemisionResumen` as the source of truth (server-stamped `hora*` timestamp) rather than an optimistic local guess; requires `permisoOperarRemisiones`. From `enObra` onward, `DeliveryDetailScreen` also exposes `PruebaConcretoScreen` (Operador de Bomba only, only once a Remisión exists) — a real `POST /pruebas-concreto-fresco` field test (revenimiento/masa unitaria/temperatura/rendimiento), client-stamped with the submission moment since it's a field test performed at delivery time. `DeliveryDetailScreen`'s firma/evidencia rows (below) stay visible but render via `ActionRow`'s `enabled` flag (dimmed colors, `onTap` swapped to `null` so `InkWell` no-ops) until `_hitoAlcanzado(detalle, HitoEntrega.descargando)` — signing off or attaching evidence before the truck has actually reached "Descargando" would let a driver confirm a delivery that hasn't happened yet, so both rows sit there disabled rather than disappearing (a driver should be able to see the action exists, just not use it yet), becoming enabled together once that hito is reached (checked against the same `_detalleFuture`/`_detalleOverride` the hito stepper itself uses, so advancing the hito enables them immediately without waiting on a refetch). Both rows only render at all (enabled or not) once a Remisión exists and the session holds `permisoOperarRemisiones` — without either, there's nothing to operate on, so they're hidden outright rather than shown disabled. `DeliveryDetailScreen` → `SignatureScreen` is now real too (Operador de Bomba/Olla, only once a Remisión exists and the session holds `permisoOperarRemisiones`, same gate as `PruebaConcretoScreen`): it renders the on-canvas signature pad to a PNG, requests a presigned upload URL from `operaciones`'s `POST /evidencias/presigned-url`, `PUT`s the bytes directly to that URL (straight to storage, bypassing the backend entirely — deliberately skips `AuthService.authHeaders`), then calls `OperacionesService.registrarFirma` (`POST /remisiones/{id}/firma`) with the returned `publicUrl`. `FirmaRequest.operadorId` would be the id of whoever receives at the job site (not the driver), but this app has no lookup against `administracion-service` to resolve a name to that id, and the field isn't schema-required — so it's omitted entirely; the driver's hand-typed name of who received goes in `comentarios` instead. Since `RemisionResponse` has no boolean "firmada" flag, `DeliveryDetailScreen` derives that status itself from `OperacionesService.firmasPorRemision` (`GET /remisiones/{id}/firma`) coming back non-empty, showing a green "Firmada" pill on the `ActionRow` (which now supports an optional `statusLabel`/`statusColor`, plus the `enabled` flag mentioned above) and re-fetching after `SignatureScreen` pops with `true` — at which point it also re-fetches the pedido (`ComercialService.obtenerPedido`) and rebuilds `Remision` via `copyWith` with the just-recalculated `volumenPedidoEntregado`/`volumenPedidoPendiente`, so `SummaryCard` doesn't keep showing the pre-firma snapshot until the driver backs out and re-enters "Mis entregas del día"; best-effort, so a failed refresh leaves the stale numbers rather than surfacing an error, since the firma itself already succeeded. The backend now rejects a second firma on the same remisión (409, since it would double-count delivered volume onto the pedido — see `comercial_service.dart` above) — once `firmasPorRemision` shows one already exists, tapping the row opens `EvidenciaViewerScreen` on the existing `firmaDigitalUrl` instead of reopening `SignatureScreen`. Same idea for `DeliveryPhotoScreen`'s evidencia: once `archivosPorRemision` has entries (filtered to `tipoArchivo == 'foto_evidencia'`, since that endpoint also returns non-photo attachments like the remisión's own PDF waybill), the row becomes view-only the same way the firma row does — tapping opens `EvidenciaViewerScreen` directly for a single photo, or `evidencia_fotos_screen.dart`'s `EvidenciaFotosScreen` (a read-only gallery reusing `delivery_detail_widgets.dart`'s `EvidenciaThumbnailStrip`, `Image.network` with `cacheWidth` to keep decode cheap) once there are two or more; `DeliveryPhotoScreen` itself only opens when no evidencia exists yet on that remisión. Unlike the firma row, this isn't because of a backend limit (nothing stops a remisión from having more archivos) — there's just no "add more" entry point wired up once at least one photo is on file. `DeliveryPhotoScreen` is now real too, same mechanism as `SignatureScreen`: each picked photo (camera/gallery, via `image_picker`) gets uploaded through the presigned-URL round trip, then attached with `OperacionesService.agregarArchivo` (`POST /remisiones/{id}/archivos`, `tipoArchivo: 'foto_evidencia'`) — one call per photo, since that endpoint takes a single `archivoUrl` at a time. Its `ActionRow` shows a "N fotos" pill derived from `OperacionesService.archivosPorRemision` (`GET /remisiones/{id}/archivos`) the same way `SignatureScreen`'s does from firmas. `DeliveryDetailScreen`'s "Ubicación y ruta" section (`RouteNavigationScreen`'s entry point) stays visible — labeled "Iniciar ruta" before the truck has ever left planta, "Regresar a la ruta" for any hito after that — all the way through descargando, not just until `enObra`; an earlier version hid it once the truck reached "en obra" (arrived at the site), but that was wrong: the driver may still need the map for reference, or may have backed out of `RouteNavigationScreen` before actually finishing, anywhere between salida de planta and the truck being fully unloaded. It only actually hides once `_entregaCompleta` is true — hito at descargando/entregado *and* both a firma and a foto de evidencia are already on file (checked against the same `_firmasFuture`/`_archivosFuture` the evidencia section below already loads) — genuinely nothing left to navigate for. Still mock: `DosificacionScreen` (Operador de Bomba only; mock submission, the backend's `InformePesadora` entity has no service/controller/DTO yet) / `route_navigation_screen.dart`'s `RouteNavigationScreen` (**real** turn-by-turn navigation via `google_navigation_flutter`, and also the *sender* half of live GPS tracking: once guidance starts, if `remision.remisionId != null` and the session holds `permisoOperarRemisiones`, it posts the driver's current position via `OperacionesService.enviarPosicion` every 15s — same cadence as the Dirección-side poll — until arrival or the screen closes; a failed ping is silently swallowed and retried on the next tick rather than interrupting navigation). This closes the loop with the Dirección-side live tracking above, whenever a Remisión already exists. This is also the only place that automatically advances the middle of `HitoEntrega`'s sequence rather than waiting on `DeliveryDetailScreen`'s manual stepper: right after `salioPlanta` (awaited, not fire-and-forget like the GPS ping, so the backend's sequential state machine sees them in order) it immediately also registers `enCamino` — there's no separate real-world trigger for "en camino" distinct from having just left the plant — then registers `proximoLlegar` once via `GoogleMapsNavigator.setOnRemainingTimeOrDistanceChangedListener` crossing a 1 km remaining-distance threshold (`_proximoLlegarDistanciaMetros`), guarded by `_proximoLlegarRegistrado` so it only fires once and the subscription gets cancelled right after (also cancelled on arrival, alongside the GPS timer). Without this, a driver who only ever uses "Iniciar ruta" (never touching `DeliveryDetailScreen`'s stepper mid-drive) would jump straight from `salioPlanta` to `enObra` on arrival, silently skipping both intermediate hitos. Once guidance starts, `RouteNavigationScreen` also turns on the Navigation SDK's own speedometer (`GoogleNavigationViewController.setSpeedometerEnabled`) and trip-progress-bar (`setNavigationTripProgressBarEnabled`, marked `@experimental` by the plugin itself) — both off by default, unlike the turn-by-turn header/ETA-footer which are already on by default. None of that mattered on a real device until `_start()` also called `setNavigationUIEnabled(true)` right after `startGuidance()`: the view's `initialNavigationUIEnabledPreference: automatic` only checks *once, at native-view-creation time* whether a guidance session is already running, and this screen's view mounts on its very first frame — well before `initializeNavigationSession()`/`setDestinations()`/`startGuidance()` finish awaiting — so `automatic` always saw "no session yet" and rendered a plain map; toggling the individual sub-widgets afterward did nothing since the master navigation-UI switch was never turned on. That fix surfaced a second, separate problem, also only visible on a real device: the screen's own floating back button was fine (small, top-left, doesn't cover much), but its full-width bottom "Finalizar ruta"/"Ruta terminada" bar sat exactly where the native header/footer/speedometer/trip-progress-bar render — since ordinary Flutter widgets always paint on top of an embedded platform view, that opaque bar was silently hiding all of that native chrome underneath it even though every one of those pieces really was enabled. It used to be functionally redundant with the back button (both called `_finish()`), so removing it outright (rather than just making it transparent) was tried first — but on a real device that made the *entire* native view collapse to a tiny box in a corner instead of filling the screen, so this screen's own `Stack` apparently needs that non-positioned, full-width bottom child present for the platform view to size correctly (mechanism undocumented by the plugin, confirmed by testing with/without it, force-quitting between installs to rule out a stale suspended process). `RouteNavBottomBar` is kept for that reason, just with a transparent background (its button vertically centered in the same reserved bottom band as the native ETA/footer card via an explicit `height` matching `initialPadding.bottom`, right-aligned via `Align(centerRight)`, no longer a full-width opaque bar) so the native chrome underneath stays visible. Its "Finalizar ruta"/"Ruta terminada" button now calls its own `_finalizarRuta` instead of the shared `_finish` — tapping a clearly labeled button already *is* the driver's confirmation, so it pops immediately with no `_confirmarSalida` dialog regardless of arrival state; only the ambiguous top-left back arrow (and the system back gesture, via `PopScope`) still goes through `_finish`/`_wouldInterruptRoute`/`_confirmarSalida` to guard against an accidental tap mid-route. This is the conductor-facing DiDi/Uber-style speed+progress+ETA request; Dirección's own read-only live-tracking views (`PedidoDetailScreen`'s "Ubicación en vivo", `RutasActivasScreen`) needed a different, custom-built answer for the same ask (`direccion/route_eta.dart`'s `RouteEtaTracker` + Google's Directions API, see above) since there's no active guidance session on Dirección's device to read a native speedometer/progress-bar off of — those SDK features are inherently tied to whoever's actually driving. Android also gets its own DiDi/Uber-style lock-screen/status-bar card, separate from all of the above and from the Navigation SDK's own mandatory foreground-service notification (which this app doesn't build and can't customize — it's inside the closed-source native SDK): `lib/deliveries/navigation_live_update.dart`'s `NavigationLiveUpdate` is a `MethodChannel` wrapper (`fn_concretos/navigation_live_update`, handled in `MainActivity.kt`) around `android/app/src/main/kotlin/com/fnconcretos/app/NavigationLiveUpdateManager.kt`, which posts/updates/cancels a `NotificationCompat.Builder` styled with `ProgressStyle` and `setRequestPromotedOngoing(true)` — Android 16's "Live Update" API (`androidx.core` 1.16+; `POST_PROMOTED_NOTIFICATIONS` declared in `AndroidManifest.xml`). `RouteNavigationScreen` calls `start()` once guidance begins (independent of `permisoOperarRemisiones`/`remisionId`, unlike the GPS ping/hitos — it's a pure UX nicety, the driver is navigating either way) and `update()` from the same `setOnRemainingTimeOrDistanceChangedListener` that drives the `proximoLlegar` auto-hito above, computing a 0–100% progress bar against the first remaining-distance reading as the route's total (same "first reading is the baseline" idiom as `direccion/route_eta.dart`'s `RouteEtaTracker`); `stop()` fires on arrival and in `dispose()` (covers exiting early). The notification needs an explicit `PendingIntent` (`setContentIntent`, targeting `MainActivity` with `FLAG_ACTIVITY_REORDER_TO_FRONT`) to reopen the app on tap — Android doesn't do this by default for a bare `notify()` call, and this went unnoticed at first since without it tapping just silently did nothing. Actually seeing the *promoted* card (not just an ordinary progress notification) additionally requires the user to manually enable "Live updates" for this app under system Settings (`canPostPromotedNotifications()`, not surfaced by this screen) — and, confirmed against a real device, requires the OS build to actually support the feature: base Android 16 always renders `ProgressStyle`/`setRequestPromotedOngoing` notifications as ordinary ones regardless of what the app does, real promotion only shipped in a later quarterly platform release, so a phone/OEM skin that hasn't received that update yet will never show the card no matter how correct this code is. Tapping it reopens the app (`setContentIntent`) but, on some OEM skins (confirmed on a real device), Android has already destroyed the backgrounded Activity/task by then even though the process (and the Navigation SDK's foreground service keeping guidance/voice going) is still alive — so instead of resuming exactly where the driver left off, the tap cold-starts Flutter fresh, landing on whatever `main.dart` normally opens to. Rather than attempt to reconnect into the still-live native guidance session (uncertain whether the SDK supports that at all), the notification's `PendingIntent` also embeds the remisión id as an extra (`MainActivity.EXTRA_REMISION_ID`) so the tap can deep-link to `DeliveryDetailScreen` for that delivery instead — "Regresar a la ruta" from there re-opens the map normally. Two different paths feed that id to Dart depending on whether the tap found the app already running: a warm resume (Activity still alive, `launchMode="singleTop"`) hits `MainActivity.onNewIntent`, which pushes it straight to Dart via the same method channel (`onNotificationTap`) since Dart is definitely already up by then; a cold start only has the launch `Intent` to go on, captured once in `configureFlutterEngine` and handed to Dart on request via `consumeLaunchRemisionId()` (`main.dart` calls it once right after `runApp`, since Dart can't be pushed to reliably that early — same race `_handleNotificationClick`'s OneSignal handling already deals with, factored out here as the shared `_navigatorReady()` retry). Either path ends at `main.dart`'s `_handleRouteNotificationTap`, which calls `deliveries/entregas_service.dart`'s `EntregasService.remisionPorId()` — a `remisionId`-only counterpart to `entregasDelDia()`'s per-item resolution (same `OperacionesService.remisionDetalle` → `ComercialService.obtenerPedido`/`obtenerObra`/`contactoParaEntrega` chain, minus the `ProgramacionProduccion` this app doesn't have for a single out-of-context remisión, so `horaProgramada` is left blank) — to rebuild the `Remision` `DeliveryDetailScreen` needs, since the notification only carries an id, not the full object `DeliveriesScreen` would already have in memory.
- **`vehicle/`** — now real, backed by `operaciones/vehiculo.dart` DTOs and `OperacionesService`. `vehicle/vehiculo_service.dart`'s `VehiculoService.miVehiculo()` resolves the driver's own unit by fetching the fleet-wide `GET /vehiculos` and keeping the one whose `conductorAsignadoId` matches `AuthService.idEmpleado` (same cross-service id assumption as `conductorId` above) — there's no backend concept of "mi vehículo" as a single call. `VehicleScreen` shows that unit's details plus a mantenimiento-activo banner (derived from `mantenimientosVehiculo`'s `estatus`, no dedicated "is under maintenance" field), then links to `VehicleDocumentsScreen` (real `documentosVehiculo`, read-only — uploading a new document isn't wired up, though the same presigned-upload mechanism used elsewhere in this app now could back it), `VehiclePendientesScreen` (real `pendientesVehiculo`, read-only list — resolving one is a workshop/dirección action not wired here), and `VehiclePendingScreen` (real `POST /vehiculos/{id}/pendientes` to report a falla mecánica/llanta/mantenimiento/otro; requires `permisoReportarPendienteVehiculo`; the backend request has no `urgencia` field, so that selector was deliberately dropped rather than collecting input the server would discard). `VehiclePendingScreen` also supports an optional photo taken with the camera (`image_picker`): unlike `RemisionFirma`, `VehiculoPendiente` has no separate photo table — the same presigned-upload round trip (`operaciones`'s `POST /evidencias/presigned-url` + direct `PUT` to storage) just feeds its resulting `publicUrl` into `evidenciaApertura`, a plain field on the same pendiente row created by that same `POST`. There's a symmetric `evidenciaCierre` for whoever resolves the pendiente (`PATCH /pendientes-vehiculos/{id}/resolver`), but resolving isn't wired into this app at all (`VehiclePendientesScreen` stays read-only, see above). Both URLs are surfaced via a dedicated `VehiclePendienteDetailScreen` (tapping a `PendienteCard`, which now just shows a small camera-icon hint when evidence exists rather than cramming thumbnails into the list) — full descripción/fechas plus each evidencia photo shown full-width (`Image.network`, since they're already-public R2 URLs, no auth headers needed), tappable to open `EvidenciaViewerScreen`, a simple full-screen `InteractiveViewer` for pinch-to-zoom. `vehicle.dart` also derives document-expiry status (`vigente`/`porVencer`/`vencido`) client-side from a document's real `vigencia` date. `VehicleScreen` also renders the unit's 3D model (`model_viewer_plus`'s `ModelViewer`, a `.glb` viewer) when one is available: `VehiculoResponse` already echoes `modelo3dId`/`modelo3dNombre`/`modelo3dUrl` directly (resolved server-side once an admin assigns one via `modelo3d-controller`'s own catalog), so `VehiculoService.modelo3dUrlPara()` reads that first and only falls back to `OperacionesService.modelosPorTipoVehiculo()` (`GET /modelos-3d?tipoVehiculoId=`, picking the first `estatus == 'activo'` entry) for a vehículo that hasn't had one assigned directly yet — `modelo3d-controller`'s list/create/estatus endpoints otherwise back an admin-side catalog/selector this app doesn't expose (registering a model still requires the same presigned-upload round trip as everything else in this app, into R2's `modelos-3d` folder). `ModelViewer` only worked on iOS out of the box — on Android it failed with a WebView "Página web no disponible" error, since `model_viewer_plus` serves its viewer HTML (and redirects `/model` to the real R2 URL) from a plain-HTTP loopback server it spins up inside the app's own process (`model_viewer_plus_mobile.dart`'s `_initProxy`), and Android blocks cleartext traffic by default since API 28 — iOS's WKWebView exempts `localhost` from ATS by default, which is why only Android needed a fix. `android/app/src/main/res/xml/network_security_config.xml` scopes a cleartext exception to just `127.0.0.1`/`localhost` (referenced via `AndroidManifest.xml`'s `android:networkSecurityConfig`), deliberately not a blanket `usesCleartextTraffic="true"` that would affect other HTTP traffic in the app.
- **`administracion/administracion_service.dart`** (`AdministracionService`) — talks to the real `administracion` sandbox (`ApiConfig.administracion`), same `AuthService.authHeaders()` bearer pattern as the other services. HR employee records: `GET /empleados/{id}` (`EmpleadoResponse`, kept as a full DTO with every field the backend returns, not just what this app displays) backs `ProfileScreen`'s fuller identity data (nombreCompleto/puesto/área/teléfono) that `/auth/me` doesn't have. Profile photo upload reuses the presigned-URL-then-`PUT` mechanism (its own `/evidencias/presigned-url` endpoint, not `operaciones`'s), then calls `actualizarFotoPerfil`, which does a full `PUT /empleados/{id}` round-tripping the just-fetched record's other fields since that endpoint replaces the whole row (no partial PATCH).
- **`profile/`** — mixed: `MfaScreen`, `ChangePasswordScreen`, and `ProfileScreen`'s core identity fields (usuario/cargo/correo, from `AuthService.username`/`rol`/`correo`, populated via the real `/auth/me`) make real `AuthService` calls; the fuller identity fields and photo come from `AdministracionService` above. Planta/ciudad (and the `EditProfileScreen` that edited them) were removed — `/auth/me` never returned them, so there was no real data to show or edit; don't reintroduce them without a backend source. The dark-mode toggle writes `themeNotifier`; "Cerrar sesión" does a real `AuthService.logout()` before navigating back to `LoginScreen`.
- **`notifications/`** — real OneSignal Flutter SDK init (Android only for now; iOS's Push Notifications/App Groups setup wasn't done since the project only has a free Apple ID, no paid Developer Program membership yet), plus a real notification-history/inbox screen. `onesignal_service.dart`'s `OneSignalService` wraps `OneSignal.*` the same way `AuthService` wraps auth-service, and deliberately takes plain values instead of importing `AuthService` (would create a circular import — `auth_service.dart` imports this file, not the other way around). `main.dart` calls `OneSignalService.initialize()` then `registerClickListener()` before `runApp`, so a cold start via notification tap isn't missed. `AuthService._fetchMe()` (reached from `login`/`verifyMfa`/`restoreSession`) calls `OneSignalService.syncSession()` — `OneSignal.login(usuarioId.toString())` sets the OneSignal `external_id` so backend can target one specific account's device, and `rol`/`permisos` (comma-joined) go on as tags so a dashboard segment can target e.g. "todo Dirección" by `permisos contains pedidos.autorizar_credito` without this app hardcoding what counts as Dirección. Deliberately `usuarioId` (`/auth/me`'s `id`, added to `AuthService` specifically for this), not `idEmpleado` — auth-service's `MeResponse` returns both as separate fields, and `notificacion-controller`'s `NotificacionCreateRequest.usuarioId` (below) refers to the account id, not the employee record; passing `idEmpleado` there would register the wrong external id and backend notifications would never find the device. The OS push-permission prompt (`OneSignalService.requestPushPermission()`) is deliberately *not* part of `syncSession` — it's only called from `AuthService.login`/`verifyMfa` (an explicit user action), never from `restoreSession`, which runs silently off the splash screen on every app launch with a saved session; asking there would mean prompting before the user has seen anything, on every relaunch. `AuthService.logout()` calls `OneSignalService.clearSession()` (`OneSignal.logout()`) so a handed-down/shared device stops getting that account's notifications. **`OneSignalService` only covers the client half of push.** The three notifications this integration was originally requested for — nuevo pedido pendiente de autorización (Dirección), remisión que salió de ruta (Dirección), hito en `cargandoPlanta` listo para avanzar (conductor) — all fire off backend state changes in `comercial-service`/`operaciones-service`; nothing in this Flutter app observes another device's state change, so actually *sending* those requires backend code calling OneSignal's REST API (or this app's own notification endpoint below) when those events happen. Tapping a push (app closed, background, or foreground) is handled by `OneSignalService.registerClickListener()`, wired in `main.dart` to a module-level `navigatorKey` (on `MaterialApp`, needed since a push tap fires outside any screen's own `BuildContext`) that opens `NotificacionesScreen` — the backend doesn't send `referenciaTipo`/`referenciaId` as OneSignal `data` yet (title/mensaje only), so there's nothing to deep-link to yet; `main.dart`'s handler retries for up to ~2s if the navigator isn't attached yet (a cold start via tap can fire before `runApp`'s first frame).

  `notificaciones_service.dart`'s `NotificacionesService` and `notificaciones_screen.dart`'s `NotificacionesScreen` are the real in-app notification inbox, backed by `notificacion-controller` — which, despite the name, lives in the **auth-service** sandbox (same `_baseUrl` as `AuthService`), not `comercial`/`operaciones`. `GET /notificaciones` (paginated; `NotificacionesScreen` does real infinite scroll — `NotificacionesService.listar({page, size})` returns a `NotificacionesPage` with `hasMore` derived from Spring's `last` field, and the screen fetches the next page once `ScrollController` gets within 200px of the bottom), `GET /notificaciones/no-leidas/conteo` (badge count — the response is a generic `{key: count}` map with no fixed property name in the OpenAPI schema, so `contarNoLeidas()` takes whatever single value comes back rather than assuming a key), and the two `PATCH` mark-as-read endpoints are all real UI-facing calls. `POST /notificaciones` (`NotificacionCreateRequest.usuarioId`/`tipo`/`titulo`/`mensaje`/`referenciaTipo`/`referenciaId`) is documented as backend-to-backend only ("lo invocan los demas microservicios cuando ocurre un evento relevante para ese usuario") and isn't called from this app. `widgets/notification_bell_button.dart`'s `NotificationBellButton` (bell icon + unread badge, polling `contarNoLeidas()` every 15s) is shared by `home/HomeScreen` and `direccion/DireccionHomeScreen` — both shells reserve a dedicated row above their tab `Stack` for it (rather than floating it as a `Positioned` overlay) since individual tabs draw their own top-right controls inline (e.g. `DeliveriesScreen`'s "Historial" button) that an overlay would sit on top of; `DireccionHomeScreen` hides that row entirely on its Rutas tab, since `RutasActivasScreen` already has its own `AppBar` with top-right actions (fullscreen toggle, "ver todas") and reserving a second bar there would just eat into the map's "pantalla completa". A tab's own top-right action icon (`DeliveriesScreen`'s "Historial", `asesor_comercial/VisitasScreen`'s "+") always sits *before* the bell in that row, not after — and uses `widgets/header_icon_button.dart`'s `HeaderIconButton` rather than a bare `IconButton`, so it matches the bell's circular-chip styling (same size/tint/border/shadow) instead of looking like a mismatched plain icon next to it; both the ordering and the bare-`IconButton` styling were explicitly called out as wrong and fixed. This only applies to a tab body's own hand-built header row (no `AppBar` of its own) — `RutasActivasScreen`'s `AppBar.actions` is a different, already-standard Material pattern and deliberately wasn't switched to `HeaderIconButton`. Tapping a notification card marks it read (optimistic local update, best-effort `PATCH` — a failed call doesn't roll back the UI or surface an error, since a stale read-receipt isn't worth interrupting for) but doesn't navigate anywhere off `referenciaTipo`/`referenciaId`: the backend hasn't documented what concrete `referenciaTipo` strings it sends, so this app shows the notification itself rather than guessing at a deep-link contract that could point somewhere wrong.

## Conventions to note

- UI copy (anything the user sees on screen) is in Spanish. Code — folder/file names, class/variable names, and comments — is in English. Don't mix the two the wrong way.
- Brand color is yellow, `AppColors.accent` (`lib/theme/app_colors.dart`, literal `Color(0xFFFFCC00)`). For accents (icons, highlights, active-nav-item circle), always use `AppColors.accent` rather than reading `colorScheme.primary` — Material3's tonal palette generation shifts the seed into a duller, less saturated yellow for the `primary` role. This was called out explicitly after `colorScheme.primary` crept into `profile_screen.dart` and the now-removed `placeholder_content.dart`; screens used to each hardcode the literal locally (and a couple drifted to a slightly different one) until `AppColors` consolidated it.
- Theme-aware card surfaces (e.g. `profile_screen.dart`'s settings cards) avoid the seed-derived `colorScheme.surfaceContainerHighest` (skews yellow on this app's yellow-seeded `ColorScheme` — rejected explicitly). Pattern instead: dark mode solid near-black `Color(0xFF141414)` with a light border; light mode white with a black-ish border (a black fill reads as a stray error state on a light background); text/icon colors computed per-theme to match since the card color isn't sourced from `Theme.of(context)` directly. This pattern recurs across `deliveries/`, `vehicle/`, and `direccion/` screens, not just `profile/` — `AppColors.card`/`surfaceAlt`/`border`/`text`/`mutedText` (all take `BuildContext`) and `widgets/field_group.dart`'s `FieldGroup` container now centralize it; prefer those over a fresh local `isDark ? ... : ...` ternary.
- Logo image (`assets/images/logo.png`) is expected to exist; screens fall back to an icon via `errorBuilder` if missing. `background.png` is unused — `LoginScreen`'s background is `assets/images/login.png` (a full-screen `Image.asset`/`BoxFit.cover`, with the login card's frosted-glass `BackdropFilter` blur sitting on top of it). It used to be the pure-`CustomPainter` `LoginBackground` widget (an animated drifting grid/dots effect, no image asset) — that widget was deleted once this image replaced it, since nothing else used it. The splash screen instead depends on `assets/video/splash.mp4` (`video_player`) — its background color, `Color(0xFF15181B)`, must stay in sync with the native launch screens (`android/app/.../drawable/launch_background.xml`, `ios/Runner/Base.lproj/LaunchScreen.storyboard`) so there's no visible flash before the video's first frame.
- Network calls throughout `auth_service.dart`/`comercial_service.dart`/`operaciones_service.dart`/`administracion_service.dart` swallow transport errors into a generic `AuthException('No se pudo conectar con el servidor')` rather than surfacing raw exceptions — follow that pattern for any new service call so error handling stays consistent.
- Prefer `AppSnack.success`/`.error`/`.info` (`lib/widgets/app_feedback.dart`) over a raw `ScaffoldMessenger`/`SnackBar` call for user-facing feedback — it matches the app's themed card styling instead of Material's default grey bar.
