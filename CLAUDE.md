# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"FN Concretera" — a Flutter app for a concrete company. Note the package name in `pubspec.yaml` is `fn_concretos`, even though the directory/repo is `my_flutter_app`.

The app has grown from a UI-only prototype into a role-scoped mobile client with real backend calls for auth and for one office workflow (credit authorization), plus several feature areas that are still mock/local state. There's no single "the app does X" description — which parts are real vs. mocked varies screen by screen (see Architecture below), so check the specific screen before assuming either way.

`vistas.md` (repo root) is the product spec this build follows: it defines the three roles this app targets (Operador de Olla, Operador de Bomba, Dirección) and explicitly calls out backend gaps that block real functionality (e.g. `InformePesadora` has no service/controller/DTO yet; `ClienteService.estadoCuenta` is a stub that always answers "finanzas-service aún no está disponible"). Read it before deciding whether a feature needs backend work first or can just be wired up.

## Commands

- Install dependencies: `flutter pub get`
- Run the app (choose a connected device/simulator): `flutter run`
- Static analysis (uses `flutter_lints` via `analysis_options.yaml`): `flutter analyze`
- Format code: `dart format .`
- Run tests: `flutter test` (there are currently no test files in the project)
- Build platform targets as needed: `flutter build apk`, `flutter build ios`, `flutter build macos`, `flutter build web`, etc.

There is no CI config and no custom build scripts — this is a stock `flutter create` project structure. Native Android/iOS projects require a Google Cloud API key with "Maps SDK" and "Navigation SDK" enabled (see `route_navigation_screen.dart` below) — without it the map loads blank/greyed out and in-app turn-by-turn errors out; the Navigation SDK is billed separately from the Maps SDK.

## Architecture

`lib/` is organized by feature folder, each holding its screen(s) plus any content specific to that screen; `lib/widgets/` holds components shared across features. Screens navigate via `Navigator.push`/`pushReplacement` with `MaterialPageRoute` — there is no named-route table or router package, and no state-management package (no Provider/Riverpod/Bloc) — each screen manages its own local `State`. `main.dart`'s `themeNotifier` (a top-level `ValueNotifier<ThemeMode>`, default `ThemeMode.dark`, that `MaterialApp` listens to) and `AuthService`'s static session fields are the only pieces of state shared across screens; both use the same "static field, no package" pattern rather than introducing one.

**Navigation is role/permission-branched, not a single fixed flow.** `main.dart` → `SplashScreen` (3s delay) → `LoginScreen` → real login against `AuthService`, then routed by `LoginScreen._navigateAfterLogin`:
- Role name in `roles.dart`'s `rolesConAppMovil` (`Operador de Olla`, `Operador de Bomba`) → `home/HomeScreen` (field-ops shell: Entregas/Vehículo/Perfil tabs).
- Otherwise, holding the `pedidos.autorizar_credito` permission → `direccion/DireccionHomeScreen` (Autorizaciones/Perfil tabs).
- Anyone else → `auth/RoleUnavailableScreen` (explains the role has no mobile screens yet, points to the desktop system, offers logout).

Both shells reuse the same tab pattern: all tabs stay mounted and are cross-faded (`AnimatedOpacity` + `AnimatedScale`, not `IndexedStack`) so tab state survives switching, with a floating `widgets/bottom_nav_bar.dart` (`BottomNavBar`, icon-only pill nav, active item gets a solid accent-colored circle; exposes `BottomNavBar.clearance(context)` for scrollable screens to pad their bottom content).

Dirección's routing is deliberately by *permission*, not role name, per a comment in `direccion/comercial_service.dart`: the backend's roles-controller can reassign permissions to a different/renamed role independently of this app, so hardcoding a role-name check would silently break if that happens. `auth/roles.dart` keeps a static `catalogoRoles` mirroring the backend's `/roles` catalog purely so screens can show a role's Spanish name/description without a network round trip.

### Real backend calls vs. mock data — check per screen

- **`auth/auth_service.dart`** (`AuthService`) — talks to the real `auth-service` sandbox (`https://fnconcretos.app/sandbox/auth`, see its `/v3/api-docs`). Session (access/refresh tokens, `username`, `rol`, `permisos`, `mfaHabilitado`) lives in static fields, refreshed transparently before each authenticated call (`_ensureFreshToken`). Covers login, MFA enroll/verify (TOTP), forgot/reset/change password, logout. `LoginScreen` handles `MfaRequiredException` with an in-place TOTP dialog. `POST /auth/validate` is deliberately unimplemented — it's an API Gateway/inter-service introspection endpoint, not something a mobile client calls. The API docs mark MFA enrollment as mandatory for Dirección/Pagos, but the backend doesn't block login over it; the app enforces that itself — `ProfileScreen`'s MFA tile shows real status from `mfaHabilitado`, and `direccion/DireccionHomeScreen` shows a one-time-per-session dialog nudging enrollment when `mfaHabilitado == false` (deliberately dismissible with "Más tarde" rather than a hard lock, since there's no confirmed backend-side enforcement to mirror). Pagos isn't affected — it has no mobile screens at all (not in `rolesConAppMovil`), so it never reaches a screen where this could be enforced.
- **`direccion/comercial_service.dart`** (`ComercialService`) — talks to the real `comercial` sandbox (`https://fnconcretos.app/sandbox/comercial`), reusing `AuthService.authHeaders()` for bearer auth. Backs `AutorizacionesScreen` (live list of pedidos pending credit authorization) and `PedidoDetailScreen` (cliente + estado de cuenta lookup, aprobar/rechazar). `EstadoCuenta.disponible == false` means the estado-de-cuenta call is answering from a stub, not real account data — surface that distinction, don't treat a stubbed response as a real "cliente al corriente". `pedido.dart` also holds `Obra` (`obtenerObra`) — a pedido's job site, with the lat/lng used for maps/navigation.
- **`operaciones/operaciones_service.dart`** (`OperacionesService`) — talks to the real `operaciones` sandbox (`https://fnconcretos.app/sandbox/operaciones`), same auth-header pattern as `ComercialService`. Lives in its own top-level folder (not under `direccion/`, despite originating there) because it's consumed by `direccion/`, `deliveries/`, and `vehicle/` — same reasoning as `auth_service.dart` living in `auth/` rather than any one screen's folder. Backs: `direccion/PedidoDetailScreen`'s "Ubicación en vivo" section (fetches the pedido's remisiones via `GET /remisiones?pedidoId=`, then polls `GET /remisiones/{id}/ruta` every 15s to render current position + trail on a `GoogleMapsMapView` — read-only map view from the same `google_navigation_flutter` package used for driving navigation, no extra dependency/API key needed; a pedido can have more than one remisión — e.g. olla and bomba — so this section renders one live-tracking card per remisión found); `deliveries/EntregasService` (below), via `programacion-produccion` and `asignaciones`; the hito state machine (`avanzarHito`, `remisionDetalle`) and GPS reporting (`enviarPosicion`) also used by `deliveries/`; `pruebas-concreto-fresco` field tests; and the `vehiculos`/`mantenimientos`/`pendientes-vehiculos`/`documentos` family of endpoints backing `vehicle/` (below). Two module-level permission constants gate write calls: `permisoOperarRemisiones` (`'remisiones.operar'`, required for `enviarPosicion`/`avanzarHito`/`registrarPruebaConcreto`) and `permisoReportarPendienteVehiculo` (`'vehiculos.reportar_pendiente'`, required for `registrarPendienteVehiculo`).
- **`deliveries/`** — `DeliveriesScreen` ("Mis entregas del día") is real, built by `entregas_service.dart`'s `EntregasService.entregasDelDia()`, which chains three independent services with no shared knowledge of each other: `operaciones`'s `GET /programacion-produccion?fecha=` (the *whole plant's* schedule for the given day, not per-driver — `HistorialEntregasScreen` reuses the same call with a past date the conductor picks, since it takes an arbitrary `fecha`) → `operaciones`'s `GET /asignaciones?pedidoId=` (filtered client-side to keep only rows where `conductorId == AuthService.idEmpleado`, on the assumption that `auth-service`'s `idEmpleado` and `operaciones-service`'s `conductorId` share the same id space — unverified, flagged in code) → `comercial`'s `obtenerPedido`/`obtenerObra` for job-site details and lat/lng. `EntregasService` also does a best-effort `OperacionesService.remisionesPorPedido` lookup (same call `direccion/PedidoDetailScreen` uses) to see if planta/producción already generated a Remisión for the pedido, filtered to this conductor's own — if so, `Remision.remisionId`/`hitoActual` are set from the real `RemisionResumen.estatus`; **the app never creates a Remisión itself** (would need fields like `metrosCargados` the driver's phone has no way to know), so no Remisión yet just means `remisionId`/`hitoActual` stay null and `DeliveryDetailScreen`'s hito stepper doesn't render (`_HitoChip` shows a plain "Programado" chip instead). Once a Remisión exists, `DeliveryDetailScreen`'s stepper walks `HitoEntrega`'s 7-step sequence (`cargandoPlanta` → `salioPlanta` → `enCamino` → `proximoLlegar` → `enObra` → `descargando` → `entregado`, excluding the non-sequential `conIncidencia`) by calling the real `OperacionesService.avanzarHito`, which returns the updated `RemisionResumen` as the source of truth (server-stamped `hora*` timestamp) rather than an optimistic local guess; requires `permisoOperarRemisiones`. From `enObra` onward, `DeliveryDetailScreen` also exposes `PruebaConcretoScreen` (Operador de Bomba only, only once a Remisión exists) — a real `POST /pruebas-concreto-fresco` field test (revenimiento/masa unitaria/temperatura/rendimiento), client-stamped with the submission moment since it's a field test performed at delivery time. Also still real/mock as before: `DeliveryDetailScreen` → `SignatureScreen` (on-canvas capture, confirms locally, no backend write) / `DeliveryPhotoScreen` (camera/gallery capture is real via `image_picker`, but "Guardar evidencia" is a mock save — no upload endpoint exists yet) / `DosificacionScreen` (Operador de Bomba only; mock submission, the backend's `InformePesadora` entity has no service/controller/DTO yet) / `route_navigation_screen.dart`'s `RouteNavigationScreen` (**real** turn-by-turn navigation via `google_navigation_flutter`, and also the *sender* half of live GPS tracking: once guidance starts, if `remision.remisionId != null` and the session holds `permisoOperarRemisiones`, it posts the driver's current position via `OperacionesService.enviarPosicion` every 15s — same cadence as the Dirección-side poll — until arrival or the screen closes; a failed ping is silently swallowed and retried on the next tick rather than interrupting navigation). This closes the loop with the Dirección-side live tracking above, whenever a Remisión already exists.
- **`vehicle/`** — now real, backed by `operaciones/vehiculo.dart` DTOs and `OperacionesService`. `vehicle/vehiculo_service.dart`'s `VehiculoService.miVehiculo()` resolves the driver's own unit by fetching the fleet-wide `GET /vehiculos` and keeping the one whose `conductorAsignadoId` matches `AuthService.idEmpleado` (same cross-service id assumption as `conductorId` above) — there's no backend concept of "mi vehículo" as a single call. `VehicleScreen` shows that unit's details plus a mantenimiento-activo banner (derived from `mantenimientosVehiculo`'s `estatus`, no dedicated "is under maintenance" field), then links to `VehicleDocumentsScreen` (real `documentosVehiculo`, read-only — uploading needs an `archivoUrl` this app has no way to produce, same blob-storage gap as `SignatureScreen`/`DeliveryPhotoScreen`), `VehiclePendientesScreen` (real `pendientesVehiculo`, read-only list — resolving one is a workshop/dirección action not wired here), and `VehiclePendingScreen` (real `POST /vehiculos/{id}/pendientes` to report a falla mecánica/llanta/mantenimiento/otro; requires `permisoReportarPendienteVehiculo`; the backend request has no `urgencia` field, so that selector was deliberately dropped rather than collecting input the server would discard). `vehicle.dart` also derives document-expiry status (`vigente`/`porVencer`/`vencido`) client-side from a document's real `vigencia` date.
- **`profile/`** — mixed: `MfaScreen`, `ChangePasswordScreen`, and now `ProfileScreen`'s core identity fields (usuario/cargo/correo, from `AuthService.username`/`rol`/`correo`, populated via the real `/auth/me`) make real `AuthService` calls. Planta/ciudad have no backend source (`/auth/me` doesn't return them), so they stay local-only editable stubs in `EditProfileScreen`/`ProfileScreen` — don't assume they reflect anything real. The dark-mode toggle writes `themeNotifier`; "Cerrar sesión" does a real `AuthService.logout()` before navigating back to `LoginScreen`.
- **`visits/visit_screen.dart`** and **`widgets/placeholder_content.dart`** — orphaned: not reachable from any current navigation path (the old dashboard/quick-action flow that used them is gone). Don't assume either is live UI; confirm with a reference search before editing or removing.

## Conventions to note

- UI copy (anything the user sees on screen) is in Spanish. Code — folder/file names, class/variable names, and comments — is in English. Don't mix the two the wrong way.
- Brand color is yellow, `Color(0xFFFFCC00)`. For accents (icons, highlights, active-nav-item circle), always hardcode this literal rather than reading `colorScheme.primary` — Material3's tonal palette generation shifts the seed into a duller, less saturated yellow for the `primary` role. This was called out explicitly after `colorScheme.primary` crept into `profile_screen.dart` and `placeholder_content.dart`.
- Theme-aware card surfaces (e.g. `profile_screen.dart`'s settings cards) avoid the seed-derived `colorScheme.surfaceContainerHighest` (skews yellow on this app's yellow-seeded `ColorScheme` — rejected explicitly). Pattern instead: dark mode solid near-black `Color(0xFF141414)` with a light border; light mode white with a black-ish border (a black fill reads as a stray error state on a light background); text/icon colors computed per-theme to match since the card color isn't sourced from `Theme.of(context)` directly. This pattern recurs across `deliveries/`, `vehicle/`, and `direccion/` screens, not just `profile/`.
- Background/logo images (`assets/images/background.png`, `logo.png`) are expected to exist; screens fall back to an icon via `errorBuilder` if missing.
- Network calls throughout `auth_service.dart`/`comercial_service.dart`/`operaciones_service.dart` swallow transport errors into a generic `AuthException('No se pudo conectar con el servidor')` rather than surfacing raw exceptions — follow that pattern for any new service call so error handling stays consistent.
